# 文档与开放平台

接口设计得再好，第三方开发者接触到的第一样东西是文档。他打开你的文档站，五分钟内没调通第一个接口，大概率就去找别的方案了，或者给你发一封邮件，而一人公司最缺的就是回邮件的时间。这一章讲 API 文档的结构、每一部分写什么，以及当你从「给一个合作方开个口子」走向「开放平台」时，按什么顺序补齐哪些东西。

## 文档是 API 的界面

对第三方来说，文档就是你的 API 的界面，和 App 的界面一样需要设计。它的读者有三种状态，各要不同的东西：

| 读者状态 | 想要什么 | 对应的文档 |
|---|---|---|
| 第一次来，在评估要不要用 | 能做什么、多快能跑通 | 概览 + 快速开始 |
| 正在接入 | 某个概念怎么用：认证、分页、错误、Webhook | 指南 |
| 已经接好，查细节 | 某个接口的某个参数 | 参考 |
| 已经上线，在维护 | 最近改了什么，有没有影响我 | 更新日志 |

最常见的失败是只有「参考」：一份从 OpenAPI 生成的、列着所有接口的页面。它对查细节的人很好用，对第一次来的人毫无帮助：他不知道该先调哪个接口，不知道 API key 在哪里拿，不知道分页游标要怎么用。

## 快速开始：五分钟调通

快速开始只有一个目标：**让读者在五分钟内看到第一个成功的回包**。它应该是一页、按顺序编号的几步，每一步都能直接复制执行：

````markdown
## 1. 拿到 API key

登录门店后台，打开「设置 → API key → 新建」，名字随便填，权限勾选「开支：读」。
key 只显示一次，先复制下来。测试时建议用 `hck_test_` 开头的测试 key，它只能看到测试门店的数据。

## 2. 调第一个接口

```bash
export HATCH_KEY="hck_test_..."
curl https://api.hatch-counter.example/v1/expenses?limit=2 \
  -H "Authorization: Bearer $HATCH_KEY"
```

## 3. 你应该看到

```json
{
  "items": [
    { "id": "exp_01JC3Z8Q", "amount": 3200, "note": "买纸杯", "paidAt": "2026-11-04T17:12:00+08:00" }
  ],
  "nextCursor": "eyJ2IjoxLCJrIjpb..."
}
```

金额的单位是分。`nextCursor` 不是 null 说明还有下一页，用法见「分页」。

## 4. 接下来

- 想在开支发生时收到通知：看「Webhook」
- 想写入数据：看「幂等」，所有写接口都要带 `Idempotency-Key`
````

写快速开始的检验方法是：**自己用一个全新的测试账号，严格照着文档一步步做**，任何一步需要「你懂的」知识才能继续，就是文档的漏洞。

## 指南：把横切的概念讲一次

前面九章讲的那些横切约定，每一项都对应指南里的一页：

| 指南页 | 内容来自 |
|---|---|
| 认证与 API key | [第 6 章](06-auth-rate-limit.md)：key 的格式、放在哪个头、scope、轮换 |
| 错误 | [第 2 章](02-errors.md)：Problem Details 格式、错误码表、每个码的处理建议 |
| 分页与过滤 | [第 3 章](03-pagination-filtering.md)：游标怎么用、不要解析游标、排序参数 |
| 幂等与并发 | [第 5 章](05-concurrency-idempotency.md)：哪些接口要带幂等键、412 怎么处理 |
| 限流与配额 | [第 6 章](06-auth-rate-limit.md)：429 的两种含义、`Retry-After` |
| 版本与兼容 | [第 4 章](04-versioning-evolution.md)：哪些变化你会做而不通知（新增字段、新增枚举值），客户端要怎么写才不会坏 |
| Webhook | [第 9 章](09-webhooks.md)：事件格式、验签代码、重试表、去重 |

「版本与兼容」这一页特别重要，而且很多 API 不写。它是一份**你和调用方之间的约定**：你承诺不做哪些事（不删字段、不改类型），同时声明你保留做哪些事的权利（加字段、加枚举值、加错误码）。写清楚之后，调用方因为严格校验而在你加字段时崩溃，责任就是清楚的。

每一页都用具体的例子，并给出可以复制的代码。错误码表要给出**每个码的处理建议**，而不只是含义：

| code | 含义 | 你应该 |
|---|---|---|
| `rate_limited` | 请求太快 | 按 `Retry-After` 等待后重试，不要立刻重试 |
| `quota_exceeded` | 本月额度用完 | 不要重试，提示用户升级或等待重置 |
| `version_mismatch` | 数据已被修改 | 重新 `GET`，在新数据上重做修改 |
| `idempotency_mismatch` | 同一个幂等键换了内容 | 这是你的代码的 bug：改了内容要换新的幂等键 |

## 参考：从 OpenAPI 生成

接口参考不要手写，从[第 7 章](07-openapi-codegen.md)生成的 `openapi.json` 渲染。

> [!WARNING]
> 下面提到的文档渲染工具发展较快，功能和授权方式可能变化，以各自官方网站为准。

常见的选择有 Swagger UI（最老牌）、Redoc（三栏布局，阅读体验好）、Scalar（较新，带交互式调试）。它们都能读一个 OpenAPI 文件，生成一个静态页面，部署到任何静态托管上（Cloudflare Pages、对象存储加 CDN）。

参考文档的质量取决于 OpenAPI 里写了多少。生成工具能做的只是排版，下面这些要在 schema 里写好：

- 每个接口一句 `summary`，一段 `description` 讲清副作用和注意事项（「作废会把已入库的数量从库存里扣回」）
- 每个字段的 `description`：单位、格式、取值含义、什么时候为 `null`
- 每个接口至少一个请求和回包的 `examples`
- 每个接口可能返回的错误码
- 需要的 scope

一个容易被忽视的细节：文档站本身要能被搜索。读者最常做的事是在文档里搜一个字段名或错误码。

## 更新日志

更新日志是给已经接好的人看的。格式简单，按日期倒序，每条标明类型：

```markdown
## 2026-11-01

- **新增** `GET /usage`：查询本周期的用量和额度
- **新增** 开支对象增加 `memo` 字段，与 `note` 相同
- **弃用** 开支对象的 `note` 字段，请改用 `memo`。`note` 将于 2027-05-01 移除
- **修复** `GET /expenses` 在 `from` 和 `to` 为同一天时漏掉当天最后一秒的记录

## 2026-10-15

- **行为变化** `POST /stock-orders/{id}/receive` 现在会同时生成一笔开支，对应的 Webhook 事件 `expense.created` 也会发出
```

「行为变化」要单列。它不改变接口形状，OpenAPI 的 diff 发现不了，但可能影响调用方的逻辑。

更新日志之外，**破坏性变更和弃用要主动通知**：给每个有活跃 API key 的账号发邮件。不要指望调用方会定期来看更新日志。

## 从一个合作方到开放平台

「开放平台」听起来是一个大工程。对一人公司来说，它应该是被需求一步步推出来的，而不是提前建好等人来。

| 阶段 | 触发条件 | 要有的 | 不需要的 |
|---|---|---|---|
| 0 | 没有第三方 | 内部接口按本书的约定设计 | 文档站、开发者后台 |
| 1 | 第一个合作方 | 手动发一个 API key、一页快速开始、一份 OpenAPI | 自助申请 |
| 2 | 几个合作方，同样的问题被问第二遍 | 门店后台里的 API key 管理、Webhook 端点管理和投递日志、完整的文档站、测试 key | 应用市场、OAuth |
| 3 | 有人想做「给很多门店用」的应用 | OAuth 授权（门店授权第三方应用访问）、应用审核、开发者条款 | |

阶段 1 到阶段 2 的判断标准是：**同一个问题被问到第二遍**。第一次回答写进邮件，第二次就该写进文档；第一次手动发 key，第三次就该做自助的 key 管理。

阶段 3 是一个本质的变化：从「门店自己接自己的系统」变成「第三方做一个应用，让很多门店授权使用」。这时 API key 不够用了（一个应用不能找每家门店要 key），需要 OAuth；也需要审核应用、处理数据授权和撤销。这个阶段的工作量很大，在真的有人要做这样的应用之前，不要开始。

### 测试环境

阶段 2 起，接入方需要一个可以随便折腾、不影响真实数据的环境。两种做法：

| 做法 | 说明 | 成本 |
|---|---|---|
| 独立的测试部署 | `sandbox.api.hatch-counter.example`，单独的数据库 | 多维护一套部署，两边的代码版本要一致 |
| 同一部署里的测试门店 | 测试 key 只能访问被标记为测试的门店，测试门店的数据定期重置 | 几乎为零，但要保证测试门店的操作不触发真实的副作用（短信、扣费） |

一人公司推荐第二种。实现上，给门店加一个 `is_test` 标记；测试 key 的守卫只放行测试门店；发短信、调付费的识别服务、发真实 Webhook 这些出站调用，在测试门店上替换为假的实现（或者走对方的测试环境）。

### 开发者后台

阶段 2 的「开发者后台」不需要是一个独立的产品，就是门店后台里「设置」下面的几个页面：

- **API key**：列表（名字、前缀、scope、最后使用时间）、新建、撤销
- **Webhook**：端点列表、订阅的事件类型、密钥轮换、投递日志、发送测试事件
- **用量**：本周期各项用量和额度，最近的限流次数

这些页面同时也是你自己排查问题的工具。合作方说「没收到通知」，你和他看的是同一份投递日志。

## 开放之后的运营

API 开放出去之后，日常要多做几件事：

- **按调用方看监控**：请求量、错误率、延迟都按 API key 分组看。一个 key 的错误率突然升高，多半是对方上了有 bug 的新版本，主动发封邮件，比等对方来找你体验好得多
- **关注弃用接口的调用方**：[第 4 章](04-versioning-evolution.md)的弃用拦截器记下的调用记录，是逐个通知的依据
- **状态页**：一个简单的、独立部署的页面，写明当前是否有故障。出故障时，合作方第一件事是来看这个页面，而不是给你打电话
- **一个固定的支持渠道**：一个邮箱或一个工单入口，并在文档里写明大致的响应时间。不要让合作方加你的私人微信，否则你会在凌晨被问参数怎么填

> [!WARNING]
> 涉及个人信息和数据共享的合规要求按凭记忆的一般原则概括，可能已调整，具体以《个人信息保护法》等法律法规及网信办等主管部门的最新规定为准，必要时咨询专业律师。

还有一件事不能忘：**第三方通过 API 拿到的是你用户的数据**。门店授权收银系统读取开支，开支里可能有店员的姓名；授权读取会员数据，那就是顾客的手机号。开放前要想清楚：哪些数据可以通过 API 给出、门店授权时要看到怎样的说明、授权能不能随时撤销、撤销后对方手里的数据怎么办。这些写进开发者条款，也写进门店那一侧的授权页面。

## 让 AI 也能读

2026 年，读你文档的已经不只是人。接入方很可能让编程 Agent 去读文档、写对接代码。这对文档提出了一点新的要求，好在和对人友好的要求基本一致：

- **OpenAPI 文件可以直接下载**：Agent 读结构化的 OpenAPI 比读渲染后的 HTML 准确得多。在文档首页放一个明显的下载链接
- **纯文本版本**：有些文档站会提供一个汇总全部文档的 Markdown 文件，或者按 `llms.txt` 的惯例在站点根目录放一份索引，方便 Agent 一次读完
- **例子完整、可运行**：Agent 和人一样，最依赖的是能直接照抄的例子；省略号和「略」会让它们猜，猜错的地方就是 bug
- **约定写成明确的规则**：「游标是不透明字符串，不要解析」「改了内容要换新的幂等键」这样的句子，Agent 能照做；散落在段落里的暗示，它会漏掉

> [!NOTE]
> `llms.txt` 目前是社区提出的惯例而不是正式标准，各家支持程度不一。提供一份纯 Markdown 的文档汇总成本很低，但不要指望它替代结构清楚的 OpenAPI 和指南。

## 本章要点

- 文档的读者有四种状态，分别对应概览与快速开始、指南、参考、更新日志
- 快速开始的目标是五分钟内看到第一个成功回包，用全新账号严格照做来检验
- 横切的约定（认证、错误、分页、幂等、限流、兼容、Webhook）在指南里各讲一次；错误码表写处理建议
- 「版本与兼容」页写明你承诺不做什么、保留做什么
- 参考文档从 OpenAPI 生成，质量取决于 schema 里的说明和示例
- 更新日志按日期倒序、单列行为变化；破坏性变更和弃用主动邮件通知
- 开放平台按需求推进：一个合作方时手动发 key，同样问题问到第二遍再做自助，有人要做多门店应用时才上 OAuth
- 测试环境用同一部署里的测试门店，出站副作用替换成假的
- 开放后按调用方监控、有状态页和固定支持渠道；想清楚通过 API 给出的用户数据和授权撤销
- 文档对 Agent 友好：可下载的 OpenAPI、纯文本版本、完整的例子、明确的规则

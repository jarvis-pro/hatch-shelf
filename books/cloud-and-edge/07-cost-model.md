# 成本模型与账单控制

按量计费的云服务，账单不是「一个月多少钱」，而是「你的用量乘以一张单价表」。看懂计费模型，才能在写代码时就知道哪一行会花钱；不看懂，就只能等月底账单来了再吓一跳。本章不写任何具体单价（它们经常变，以各家定价页为准），只讲**计费维度、估算方法和放大器**，用 hatch-recordwall 的曲库做一次完整估算，最后讲怎么给账单装上限。

通用的成本管理方法（成本清单、固定与变动成本、单位成本、每月回顾、自建还是托管的时间账）在[《一人运维手册》第 6 章](../production-ops/06-cost-control.md)已经讲过，本章专注于云和边缘服务特有的部分。

## 账单的通用公式

几乎所有按量计费的服务都可以写成：

$$
\text{月账单} = \text{套餐底价} + \sum_{i} \max(0,\ \text{用量}_i - \text{免费额度}_i) \times \text{单价}_i
$$

要做的事只有三步：

1. **列出维度**：这个服务按哪几项计费
2. **估算用量**：你的业务每个月在每个维度上用多少
3. **代入单价**：查当前定价页，算出结果，再乘一个安全系数

难点在第 2 步：用量要从业务行为推出来，而不是凭感觉。

## 各服务的计费维度

### Cloudflare 开发者平台

| 服务 | 计费维度 | 不收费或很少收费的项 |
|---|---|---|
| Workers | 请求数、CPU 时间 | I/O 等待的墙钟时间不计 |
| R2 | 存储容量（GB·月）、A 类操作（写、列举等）、B 类操作（读等） | **出网流量不收费** |
| KV | 读、写、删除、列举次数，存储容量 | |
| D1 | 读取行数、写入行数、存储容量 | |
| Durable Objects | 请求数、运行时长（按内存 × 时间）、存储 | WebSocket 休眠期间不计时长 |
| Queues | 操作次数 | |

付费套餐通常有一个月度底价，并包含一定的免费用量；免费套餐有每日或每月的额度，超出后的行为（拒绝请求还是转为计费）要事先确认。**这些规则以 Cloudflare 当前的定价和限制页面为准**。

### 传统云（国内云和海外云都适用）

| 资源 | 常见计费方式 | 要算的 |
|---|---|---|
| 云服务器 | 包年包月 / 按量；带宽按固定带宽或按流量 | 实例规格、磁盘、公网带宽或出网流量 |
| 对象存储 | 容量 + 请求次数 + **出网流量** + 取回费 | 下载量大时出网流量往往是大头 |
| CDN | 按流量或按带宽峰值；HTTPS 请求数可能单独计 | 被刷时增长最快的一项 |
| 托管数据库 | 实例规格按时长 + 存储 + 备份 | 底价高，与用量关系小 |
| 函数计算 | 调用次数 + 资源用量（内存 × 时长）+ 出网流量 | 按墙钟时长计费的平台，等待 I/O 也花钱 |

最后一行值得注意：**有的函数平台按内存 × 墙钟时长计费，Workers 按 CPU 时间计费**。前者在调用慢的上游 API 时，等待的每一毫秒都在花钱；后者等待不花钱。同样的代码在两个平台上的成本结构可能完全不同。

## 估算：从业务行为推用量

以 hatch-recordwall 的曲库为例。它的业务行为很清楚：

- 发布者把一首歌上传进来：写一个音频对象、一个封面对象、可能一个歌词对象，再读-改-写一次目录
- 订阅者打开 App：拉 manifest，再拉变了的目录分片
- 订阅者下载一首歌：一次（或几次）带 Range 的读

把它写成变量：

| 变量 | 含义 |
|---|---|
| $S$ | 每月新上架的歌曲数 |
| $U$ | 订阅者人数 |
| $d$ | 每个订阅者每月下载的歌数 |
| $o$ | 每个订阅者每月打开 App 同步目录的次数 |
| $m$ | 每首歌的平均大小（GB） |
| $T$ | 曲库累计的歌曲总数 |

推出各维度的月用量：

| 维度 | 用量公式 | 说明 |
|---|---|---|
| R2 存储 | $T \times m$（加上封面歌词，量级小） | 只增不减，是唯一随时间累积的项 |
| R2 A 类操作（写） | 约 $S \times 4$ | 音频、封面、歌词各一次，目录一次；条件写冲突时多几次 |
| R2 B 类操作（读） | $U \times (d + 2o)$ | 每次下载一次读；每次同步约读 manifest 和一个分片 |
| Worker 请求 | 约等于 R2 操作总数 + ping 等 | 每个操作都经过 Worker |
| Worker CPU 时间 | 请求数 × 每请求几毫秒 | 字节是流式转发的，不随文件大小增长 |
| 出网流量 | $U \times d \times m$ | R2 不收费；放在按流量收费的存储上，这一项就要算钱 |

几个人的私人曲库，这些数字都很小：大概率落在免费额度或底价之内。但这张表的价值在于**看清结构**：

- 唯一持续增长的是**存储容量**，它随曲库规模线性累积
- 下载流量是潜在的最大项，R2 不收出网费，让这一项消失了。同样的业务放在按出网流量计费的对象存储上，$U \times d \times m$ 很快会超过其他所有项之和
- CPU 时间和文件大小无关，因为 Worker 没有把字节读进内存处理

这也是第 1 章说「组合是常态」的成本依据：**大文件下载放在不收出网费、或出网费低的地方**。

## 放大器：让账单失控的写法

估算出来的数字通常不会错得离谱，账单失控几乎都来自「放大器」：一个用户行为触发了远超预期的计费操作。

| 放大器 | 发生了什么 | 怎么防 |
|---|---|---|
| 公共读被盗链、被刷 | 任何人都能无限次下载 | 不设公共读，前面挡鉴权（第 3 章） |
| 客户端重试风暴 | 服务端出错，所有客户端同时快速重试 | 指数退避 + 随机抖动 + 重试上限 |
| Range 切得太碎 | 一个文件按 64KB 一段下载，一首歌几十次读操作 | 分段尽量大，或一次请求整个文件 |
| 轮询代替推送 | 每个客户端每几秒请求一次「有没有更新」 | 拉长间隔、用 manifest 比对、真需要实时再用推送 |
| 频繁列举 | 每个请求都 `list` 一次桶 | 维护 manifest，列举放到后台任务 |
| D1 全表扫描 | 缺索引的查询每次读成千上万行 | 建索引，`EXPLAIN QUERY PLAN` |
| DO 不休眠 | 持有 WebSocket 的实例一直在内存里计时长 | 用休眠 API |
| 日志过量 | 每个请求打大量日志，观测服务按量计费 | 控制日志量和采样率 |
| 开放代理 | 转发接口被拿去请求任意地址 | 目标白名单（第 4 章） |
| 递归调用 | Worker 请求了自己的域名，自己调自己 | 检查子请求的目标，避免回环 |

前两条最值得警惕。唱片墙的设计在这两点上都很保守：桶完全私有，所有访问都要令牌；转发接口只认白名单里的几个域名。README 里明确写了白名单是「这条路唯一的安全边界」，因为只读令牌曾经跟着测速脚本发出去过，不能假设它不会落到别人手里。

## 给账单装上限

### 第一层：在架构上让「被刷」不可能

最可靠的上限不在账单设置里，而在架构里：

- **没有令牌拿不到任何东西**：私有桶 + 鉴权网关，盗链和爬虫无从下手
- **令牌可以吊销**：只读令牌泄露了就换一把；写令牌不进任何安装包
- **按身份限流**：对敏感接口（登录、口令、发短信）按 IP 或账号限次（第 5 章的 DO 限流示例；Cloudflare 也提供基于规则的限流功能）
- **客户端行为可控**：重试有上限、轮询有间隔、下载有并发上限

### 第二层：用量告警

- Cloudflare 控制台可以配置账单和用量相关的通知，具体支持哪些指标以控制台为准
- 国内云普遍支持按金额的预算告警和余额告警
- 告警推到你一定能收到的渠道（[《一人运维手册》第 7 章](../production-ops/07-on-call.md)），阈值设在「正常用量的几倍」而不是「预算上限」，要在失控早期就知道

### 第三层：硬性停止

真正的「花到这个数就停」并不是每家都有：

| 机制 | 例子 | 注意 |
|---|---|---|
| 免费套餐的额度 | 超出后请求被拒绝而不是计费 | 适合个人项目和早期验证；确认清楚超额行为 |
| 预付费 / 余额 | 余额用完停服 | 国内云常见；停服本身也是事故，余额告警要先于停服 |
| 服务级用量封顶 | 部分 CDN 支持流量达到阈值后停止服务 | 被刷时能止损，但正常用户也会受影响 |
| 自己写的熔断 | 定时任务查用量，超阈值就把 Worker 切到维护模式 | 最灵活，要自己维护 |

截至写作时，Cloudflare 的付费套餐没有一个通用的「花到多少就停」开关，以控制台和文档的最新情况为准。所以对付费套餐上的服务，**第一层的架构防线最重要**。

一个简单的应用层熔断思路：在 KV 里放一个开关，Worker 每个请求读一下（KV 读很便宜、有边缘缓存），定时任务或你手动把开关打开时，除了 `/v1/ping` 一律返回 503。它比不上真正的硬上限，但能在你收到告警后一条命令止血：

```bash
npx wrangler kv key put --binding FLAGS maintenance on --remote
```

## 国内云的几个特有点

- **带宽计费方式**：固定带宽适合流量平稳，按流量适合低流量或波动大；同时要看是否有流量包、资源包可以抵扣
- **CDN 回源与内网**：服务器和对象存储放同一地域时，内网读写通常不收公网流量费；CDN 回源流量可能单独计费
- **欠费停机**：按量资源在欠费后可能被停机甚至释放，数据有丢失风险。开自动续费、留余额告警
- **资源包陷阱**：资源包按地域、按类型抵扣，买错了不抵；过期作废

## 每月十分钟

在《一人运维手册》第 6 章的每月成本回顾基础上，云和边缘服务额外看三件事：

1. **各维度用量的趋势**：存储是否按预期线性增长，请求数有没有突然的台阶
2. **最大的那一项是不是你以为的那一项**：如果出网流量或列举操作排进了前列，去找放大器
3. **免费额度还剩多少**：接近额度时，提前决定是升级套餐还是优化用量

## 本章要点

- 账单 = 底价 + Σ（超出免费额度的用量 × 单价）；单价查定价页，用量从业务行为推
- Workers 按请求和 **CPU 时间**计费，R2 按容量和两类操作计费、**不收出网费**；有的函数平台按墙钟时长计费，结构完全不同
- 对唱片墙这类业务，唯一持续增长的是存储；下载流量在按出网计费的存储上会成为最大项
- 账单失控几乎都来自放大器：公共读、重试风暴、碎 Range、轮询、频繁列举、缺索引、开放代理
- 上限分三层：架构上让被刷不可能、用量告警、硬性停止；Cloudflare 付费套餐上第一层最重要
- 每月看趋势、看最大项、看免费额度余量

# CLAUDE.md / AGENTS.md 怎么写

每个新会话的 agent 都是一个第一天上班、记性为零的同事。CLAUDE.md 就是塞到他手里的那张入职卡片：每次开工自动读一遍。这一章讲这张卡片放在哪儿、怎么加载、该写什么不该写什么，并拆解书架作者三个项目里的真实写法。

## 它是什么，不是什么

CLAUDE.md 是一份普通的 Markdown，Claude Code 在会话开始时把它的全文放进上下文。官方文档对它的定位说得很直白：**它是上下文，不是强制配置**。模型会尽量遵守，但没有任何机制保证它一定遵守。

所以从一开始就要分清两类规矩：

| 类型 | 例子 | 放哪儿 |
|---|---|---|
| 需要判断、讲道理的 | 「判断书籍结构的逻辑只写在 `@shelf/spec`」 | CLAUDE.md |
| 绝对不能错、能机器判断的 | 「不许改 `.env`」「不许 `git push --force`」 | 权限 deny、hooks（第 4 章） |

写在 CLAUDE.md 里的「绝不能 X」只是请求，不是保证。真正绝不能错的，要再加一道闸门。

## 放在哪儿、怎么加载

| 层级 | 位置 | 用途 |
|---|---|---|
| 组织 | macOS 上是 `/Library/Application Support/ClaudeCode/CLAUDE.md` | 公司统一规范，个人开发者用不上 |
| 用户 | `~/.claude/CLAUDE.md` | 你自己的所有项目通用的偏好 |
| 项目 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 入库，团队共享 |
| 项目本地 | `./CLAUDE.local.md` | 个人的项目偏好，加进 `.gitignore` |

加载规则：

- **启动目录及其所有上级目录**里的 CLAUDE.md 和 CLAUDE.local.md 在启动时全部加载，按从根到当前目录的顺序拼接，离你越近的越晚出现。它们**叠加**，不是互相覆盖
- **子目录**里的 CLAUDE.md 不在启动时加载，而是在 agent 读写那个子目录里的文件时才加载
- 冲突的指令模型可能随便挑一条，所以各层之间要保持一致

书架项目就用了「根目录 + 子目录」两层：根上的 CLAUDE.md 讲代码规范，`books/` 下的 AGENTS.md 讲写书规范。根文件里只有一句指路：

```markdown
在 `books/` 下写书的规则见 `books/AGENTS.md`，与代码无关的任务不需要读本文件。
```

改 App 代码的会话不会被写书规范占上下文；agent 一旦去碰 `books/` 下的文件，写书规范就自动进来了。

### @ 导入

CLAUDE.md 里可以用 `@路径` 导入别的文件，相对路径相对于写导入的那个文件解析，最多递归四层：

```markdown
项目概览见 @README.md，可用命令见 @package.json。

# 个人偏好（跨 worktree 共享）
- @~/.claude/my-project-instructions.md
```

两个提醒：

- **导入不省上下文**。被导入的文件和 CLAUDE.md 一起全文加载，它只是帮你组织文件。想省上下文，用按路径加载的 rules（第 3 章）或者只写「见某文件」让 agent 需要时自己去读
- 只想提到一个路径、不想导入，就用反引号包起来：写成 `` `@README` `` 就不会被展开

另外，CLAUDE.md 里的块级 HTML 注释 `<!-- ... -->` 会在注入上下文前被去掉，可以拿来给人类维护者留言而不花 token。

## AGENTS.md：一份文件给所有工具

AGENTS.md 是多家编码工具都认的约定文件名。新版 Claude Code 也能直接读它：项目里**没有** CLAUDE.md 时，就读 AGENTS.md；两者都有时，默认只读 CLAUDE.md（这个行为可以在设置里改成两者都读）。版本较老或某些特殊环境下不支持直接读，所以兼容写法仍然有用：

```markdown
@AGENTS.md

## 只对 Claude Code 生效的补充
- 改 `src/billing/` 之前先进 plan 模式
```

如果不需要 Claude 专属的补充，也可以用软链接，这正是 hatch-shelf 的做法：

```bash
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md books/CLAUDE.md   # 链接目标按链接所在目录解析，指向 books/AGENTS.md
```

软链接有两个代价要知道：Claude 的 Edit / Write 工具不会穿过软链接写入，会提示它去改链接目标 AGENTS.md；Windows 上 git 默认把软链接检出成一行文本。只在 macOS / Linux 上开发的个人项目，这两点都不是问题。

## 该写什么

判断标准只有一条：**一个能干的新同事第一天进来，不告诉他就大概率会做错的事**。具体可以分成六类。

### 1. 这是什么、长什么样

一两句话说清项目是干什么的，再给一张目录地图。hatch-shelf 用了一张表：

```markdown
| 目录 | 内容 |
|---|---|
| `app/` | Expo App（expo-router，路由在 `app/src/app/`，其他代码放在 `app/src/` 下的其他目录） |
| `packages/spec/` | `@shelf/spec`：book.yaml 的 zod schema、容错解析、导入安全规则。App 与 CLI 共用，**不得依赖 Node 或 RN 专有 API** |
| `tools/shelf-pack/` | Node CLI：check / pack / push |
```

注意第二行末尾那句加粗的约束。目录地图不只是告诉它「东西在哪」，还顺手告诉它「这里有什么边界」。

### 2. 架构原则

agent 改代码时最容易犯的错，是在离手最近的地方加逻辑。原则就是用来挡这个的。hatch-shelf 的写法：

```markdown
- **单一导入管线**：所有导入通道只负责把文件交给管线，不得各自写 `books/`
- RN ↔ WebView 通信的消息类型只在 `app/src/reader/bridge.ts` 定义
```

「只在某处」「不得各自」这种说法很有效：它给了一个可检查的判据。

### 3. 命令

agent 要闭环，就得知道怎么构建、怎么测、怎么检查。命令用代码块列出来，每条后面写一句注释。最重要的是**完成标准**：

```markdown
声明任务完成前必须通过 `pnpm typecheck`、`pnpm test` 和 `pnpm lint`。
```

这一句的价值超过其余所有内容。没有它，agent 会在「看起来改好了」的时候就收工。

### 4. 改坏了不报错的坑

这是最值钱的一类。编译器和测试能拦住的错，agent 自己会发现；拦不住的，只能靠你写下来。hatch-counter 的 CLAUDE.md 里有一条：

```markdown
**跑 `pnpm test` 之前先停掉服务端的 `dev`**：两个 tsc 抢着写 `apps/api/dist/`，
表现是一次红几十个、再跑一遍全绿，报错里一个字都不提 dev。
```

这条规矩的结构值得学：**做什么 + 不做的后果 + 症状**。写出症状，agent 遇到同样的现象时就能对上号。

### 5. 为什么

hatch-counter 和 hatch-recordwall 的 CLAUDE.md 都有一节「写代码的调子」，第一条就是「注释写为什么，不写做了什么」。它们对 CLAUDE.md 自己也是这么要求的。比较这两种写法：

```markdown
- 不要用 tsx 跑服务端
```

```markdown
- 服务端不能用 tsx 跑（esbuild 不出 emitDecoratorMetadata，
  依赖注入当场报「Nest can't resolve dependencies」）
```

第二种长了一倍，但 agent 知道了原因，就能举一反三：它会明白所有依赖装饰器元数据的地方都不能用 esbuild 系的工具，而不是只记住「tsx」这三个字母。没有原因的规矩，agent 在「看起来有更好办法」时很容易绕过去。

### 6. 提交与协作约定

Conventional Commits、提交信息语言、不加 AI 署名、代码和内容分开提交……这些不写它就会按自己的默认习惯来。hatch-counter 还给了两条示例提交信息，比任何描述都清楚。

## 不该写什么

| 不该写 | 为什么 | 放哪儿 |
|---|---|---|
| 代码里一眼能看出来的东西 | 浪费上下文，agent 读代码就知道 | 不写 |
| 只和某个目录相关的细则 | 每轮都占上下文 | 子目录 CLAUDE.md 或 rules（第 3 章） |
| 多步骤的操作流程（发版、部署） | 很少用到，却每轮都在 | Skill，或独立文档 + 一句指路 |
| 别处已经写过的正文 | 两份迟早不一致 | 写一句「见某文件」 |
| 密钥、IP、内部域名 | CLAUDE.md 通常入库 | 环境变量、本地文件 |

hatch-recordwall 把「别抄一遍」写进了 CLAUDE.md 本身：

```markdown
**几份 README 才是正文**……这一份只讲跨两个包的事，**别在这儿把它们再抄一遍**。
```

它还有一条很少见但很重要的「不该做」：

```markdown
**没有 CI，没有发版流水线。**……哪天嫌手工烦了再补，别为了「看起来完整」先把它搭起来。
```

agent 有一种倾向：看到「缺了什么」就想补上。明确写出「这是有意没有的」，能省掉很多不请自来的改动。

## 三个项目的写法对比

| | hatch-shelf | hatch-counter | hatch-recordwall |
|---|---|---|---|
| 规模 | 三个包 + 书 | 六个 app + 共享包 + 工具 | 三个 app + 共享包 + 工具 |
| CLAUDE.md 风格 | 短，表格 + 原则 + 命令 | 中等，大量链接到 `docs/` | 中等，指向各 app 的 README |
| 细则放哪儿 | `books/AGENTS.md` | `.claude/rules/` 六份按路径加载 | 各 app 的 README |
| 特色 | Expo 版本提醒：不要凭记忆写 API | 每条规矩都带「为什么」和症状 | 写明「有意没有的东西」 |

项目越大，CLAUDE.md 越应该像**目录**而不是**正文**：说清有哪些规矩、各在哪儿，正文放到按需加载的地方去。

## 一份起步模板

````markdown
# <项目名>

<一句话：这是什么、给谁用>。设计文档见 `README.md`，动手前先读相关章节。

## 结构
| 目录 | 内容 |
|---|---|
| `apps/web` | Vite + React 前端 |
| `apps/api` | NestJS + Drizzle，Postgres |
| `packages/core` | 前后端共用的业务口径，**不得依赖 DOM 或 Node API** |

## 原则
- <某类逻辑> 只写在 <某处>，别处调用它
- <某个改坏了不报错的坑>：<后果和症状>

## 命令
```bash
pnpm dev          # 起服务端和前端
pnpm typecheck    # 全仓类型检查
pnpm test         # 全仓测试（要先 pnpm db:up）
```
声明任务完成前必须通过 `pnpm typecheck` 和 `pnpm test`。

## 提交
- Conventional Commits，中文描述，写改完之后是什么样
````

起步也可以用 `/init`：Claude 会分析代码库生成一份初稿，已有 CLAUDE.md 时会提改进建议而不是覆盖。初稿通常偏「代码里能看出来的东西」，你要做的是删掉这些、补上它发现不了的那四类：原则、坑、为什么、有意没有的东西。

## 维护：把纠正变成规矩

CLAUDE.md 不是一次写完的。最有效的维护节奏：

1. agent 犯了一个错，你在对话里纠正
2. **同一个错出现第二次**，停下来，把它写进 CLAUDE.md（或者直接让 agent 自己写：「把刚才这条规矩加到 CLAUDE.md 的『原则』一节，带上原因」）
3. 定期通读一遍，删掉过时的、合并重复的、解决互相矛盾的

hatch-recordwall 的 CLAUDE.md 里甚至有一句针对过时内容的指令：仓库从 hatch-counter 拆出来之后，「仓库里要是还留着『跟掌柜眼没有关系』这类话，那是没清干净的旧话，直接删」。告诉 agent 什么是垃圾，它就能帮你清。

另外别忘了**自动记忆**和 CLAUDE.md 的分工：自动记忆是 Claude 自己记的、关于你的偏好和项目进展的笔记，存在本机；CLAUDE.md 是你写的、入库的项目规矩。团队（哪怕只是未来换了台电脑的你）都需要知道的，写进 CLAUDE.md。

## 本章要点

- CLAUDE.md 是每次会话自动加载的上下文，不是强制配置；绝不能错的事要另加权限或 hooks
- 启动目录及上级的 CLAUDE.md 启动时叠加加载，子目录的按需加载；`@` 导入能组织文件但不省上下文
- 新版 Claude Code 能直接读 AGENTS.md；要兼容老版本，用 `@AGENTS.md` 导入或软链接
- 该写的六类：结构、原则、命令与完成标准、改坏了不报错的坑、为什么、提交约定；规矩写成「做什么 + 后果 + 症状」
- 不写代码里看得出的、只和局部相关的、别处已有的；项目越大，CLAUDE.md 越应该像目录
- 同一个错出现第二次就沉淀进 CLAUDE.md，并定期清理过时内容

## 动手练习

1. **确认子目录 CLAUDE.md 是按需加载的**：建一个测试仓库，根目录 `CLAUDE.md` 写一句「本仓库用 pnpm」，`docs/CLAUDE.md` 写一句「docs 下的文件标题用中文」，`docs/a.md` 随便写几行。在根目录启动 Claude，先输入 `/context` 看记忆文件那一栏；再让它「读一下 docs/a.md」，然后再看一次。

   验证：第一次只列出根目录的 `CLAUDE.md`；读过 `docs/a.md` 之后，`docs/CLAUDE.md` 出现在列表里。

   参考答案：启动目录及上级的 CLAUDE.md 启动即加载，子目录的在 agent 读写那个目录里的文件时才加载。改 App 代码的会话不会被写书规范占上下文，就是靠这个。

2. **HTML 注释不进上下文**：在根 `CLAUDE.md` 里加一段 `<!-- 维护者备注：暗号是 blue-heron -->`。新开会话，问 Claude「不要读任何文件，只根据你已经加载的说明回答：CLAUDE.md 里的维护者备注写了什么暗号？」

   验证：它答不出暗号，或说明没看到这类备注；如果它去读了文件，从工具调用记录里能看出来，这次不算。

   参考答案：块级 HTML 注释在注入上下文前被去掉，适合给人类维护者留言而不花 token。反过来，想让 agent 知道的内容千万别写在注释里。

3. **给 `/init` 的初稿做减法**：在一个你熟悉的项目里运行 `/init`（已有 CLAUDE.md 的话先挪开备份），记下初稿行数 `wc -l CLAUDE.md`。然后逐行判断：哪些是读代码一眼就能看出来的，删掉；再补上它发现不了的原则、坑、为什么、有意没有的东西。

   验证：最终版本行数不超过 200；每一行都能归到本章「该写什么」的六类之一。

   参考答案：初稿常见的可删内容是「src 下是源码」「用 TypeScript 编写」这类；常见的缺口是完成标准和「改坏了不报错的坑」，这两类最值钱。

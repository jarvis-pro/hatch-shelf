# 常见坑

前七章讲的是「该怎么做」，这一章反过来，把用编码 agent 时最常踩的坑集中列一遍。每个坑都说清三件事：症状是什么、为什么会这样、用前面哪一章的手段去防。很多坑的根源都能追溯到第 1 章那句话：**它看到的世界就是它的上下文**。

## 先看全景

| 坑 | 症状 | 根源 | 对策 |
|---|---|---|---|
| 上下文塞满 | 长会话后期开始忘规矩、重复犯错 | 上下文被文件内容和输出挤满，压缩丢了细节 | 一事一会话、子 agent、压缩后重新注入 |
| 凭记忆写 API | 用了旧版本的写法，编译不过或运行时报错 | 训练数据有截止时间，框架在变 | CLAUDE.md 写明版本、要求先查文档 |
| 编造 | 不存在的函数、配置字段、命令参数 | 模型生成「看起来合理」的内容 | 类型检查、要求给出处 |
| 没验证就说完成 | 「改好了」但测试没跑 | 它对完成的判断是主观的 | 完成标准 + Stop hook |
| 顺手改进 | diff 远大于任务 | 看到「不完美」就想修 | 任务写清范围，看 `--stat` |
| 自作主张 | 数据对不上时自己猜一个 | 想把任务做完 | 明确「交给人拍板」 |
| 绕过检查 | `eslint-disable`、`as any`、改测试 | 被卡住时找捷径 | 规矩给出正确写法、hook 拦截 |
| 规矩失效 | 写了规矩它还是不遵守 | 规矩没加载、互相矛盾或过时 | `/context` 查看、定期清理 |
| 权限太宽 | 它做了不可逆的事 | 为了省事放开了权限 | deny 规则、隔离环境 |
| 被内容劫持 | 按网页或文件里的「指令」行事 | 读进上下文的内容都会影响它 | 只读不信、限制网络和写权限 |

下面挑几个展开。

## 上下文塞满

一个会话做了三个小时、改了五件事之后，agent 往往开始「变笨」：忘了 CLAUDE.md 里的规矩、重复读同一个文件、把前面任务的约束套到后面任务上。原因是上下文里塞满了早已无关的文件内容和命令输出；快满时触发的压缩会把前面的对话总结成摘要，规矩的细节可能就丢在这一步。

对策：

- **一件事一个会话**。做完一件事，用 `/clear` 清空对话再开始下一件。CLAUDE.md 会重新加载，规矩回到最清晰的状态
- **大量读取交给子 agent**（第 5 章），主会话只接收结论
- **压缩后重新注入关键信息**：用 `SessionStart` hook 配 `compact` matcher（第 4 章）
- **长任务写进度文件**。跨多个会话的任务，让 agent 把计划和进度写进一个 Markdown 文件，新会话从读这个文件开始，而不是依赖对话历史

## 凭记忆写过时的 API

这是 hatch-shelf 的 CLAUDE.md 专门写了一节来防的坑：

```markdown
当前为 Expo SDK 58。Expo 每个 SDK 都有破坏性变更，不要凭记忆写 API：

1. 先看 `app/package.json` 里 `expo` 的主版本
2. 查对应版本文档 `https://docs.expo.dev/versions/v<major>.0.0/`，或从 `https://docs.expo.dev/llms.txt` 找到具体页面
```

这段话的结构可以照搬到任何快速迭代的依赖上：**声明当前版本 → 承认「凭记忆会错」→ 给出查证的具体步骤和入口**。很多文档站现在都提供 `llms.txt` 这类给模型读的索引，把它写进 CLAUDE.md，agent 查起来更准。

同理，CLAUDE.md 里提到的版本号本身也会过时。升级依赖时，记得同步改 CLAUDE.md 里的版本声明，否则 agent 会按旧版本去查文档。

## 编造

agent 有时会信心十足地使用一个不存在的函数、一个框架里没有的配置项、一个 CLI 不支持的参数。对 TypeScript 代码，类型检查能拦住大部分；对配置文件、shell 命令、文档内容，就拦不住了。

对策：

- 对配置和命令，要求它**先查再写**：「这个字段在当前版本的文档里存在吗？给我文档里的原文」
- 对拿不准的事，要求它**说拿不准**。这套书的写书简报里就有一条：「拿不准的就讲原理，并提醒读者以官方文档为准」。允许说「不知道」，编造就会少很多
- 关键的配置改动，让它改完立刻跑一遍验证（启动服务、执行命令）

## 自作主张

任务里遇到模糊之处时，agent 倾向于自己选一个解释继续做下去，因为它的目标是「把任务完成」。这在大多数时候是优点，但在涉及数据和业务判断时很危险。

hatch-counter 和 hatch-recordwall 的 CLAUDE.md 里都有同一句：

```markdown
数据对不上、名字认不出这类情况**交给人拍板**，列出来让用户选，不自动猜。
```

这句话既是产品原则（界面上要让店主选），也是给 agent 的工作原则。可以推广成：**凡是猜错了代价大、又无法从代码里推断的事，在 CLAUDE.md 里写明「停下来问」**。比如数据库迁移要不要回填、一个字段删除会不会影响线上数据、两种业务口径选哪种。

## 顺手改进

你让它修一个 bug，它顺便重命名了几个变量、重构了一个函数、升级了一个依赖、给另外三个文件补了注释。每一处单独看都「更好」，但 diff 变大了，评审成本变高了，引入新问题的机会也多了。

对策：

- 任务描述里写明范围：「只改 X，不要动其他文件」
- 让它把发现的其他问题**列出来而不是修掉**：「看到其他问题记下来，最后一起告诉我」
- 在 CLAUDE.md 里写明「有意没有的东西」，比如 hatch-recordwall 的「没有 CI……别为了看起来完整先把它搭起来」

## 规矩写了却不生效

写了规矩它还是不遵守，先排查是不是这几种情况：

| 原因 | 怎么查 | 怎么修 |
|---|---|---|
| 规矩没加载 | `/context` 看 Memory files 里有没有那份文件 | 检查文件位置、rules 的 `paths` 是否还匹配 |
| 按路径的 rule 没被触发 | 它用 `grep` 而不是 Read 看的文件 | CLAUDE.md 里加「做 X 之前先读 Y」 |
| 规矩互相矛盾 | 通读所有层级的 CLAUDE.md 和 rules | 删掉一边，或明确写出例外 |
| 太长被淹没 | CLAUDE.md 超过两三百行 | 拆到 rules、Skill 或文档 |
| 写得太模糊 | 「注意性能」「保持代码整洁」 | 改成可检查的判据 |
| 本就不该靠规矩 | 绝对不能错的事 | 改用 hook、权限或测试 |

两个小坑：用软链接让 CLAUDE.md 指向 AGENTS.md 时，Edit / Write 工具不会穿过软链接写入，要改就改 AGENTS.md 本身；子 agent 里的 Explore 和 Plan 默认不加载 CLAUDE.md，派它们做的事别依赖项目规矩。

## 权限与机密

为了少点几次「允许」，很多人会把权限放得很宽，甚至用 `bypassPermissions`。大多数时候没事，直到某一次它执行了一个不可逆的操作。

几条底线：

- **`bypassPermissions` 只在容器、虚拟机里用**，不在你的主力开发机上用
- **不可逆的操作放进 deny 或 ask**：`git push`、`git reset --hard`、数据库的 reset、生产部署脚本。hatch-counter 的 `pnpm db:reset` 在生产环境直接拒绝执行、没有 `--force`，这是在工具层面兜底，比靠 agent 自觉可靠得多
- **机密文件加 Read deny**：`Read(./.env)`、`Read(./.env.*)`。一个文件一旦被读进上下文，就可能出现在后续的输出、日志、提交信息里
- **机密不写进任何会入库的文件**。hatch-recordwall 的 CLAUDE.md 花了一大段讲 `.env.production` 为什么只靠 `.gitignore` 挡着、「永远别给它补一条 `!` 例外」。这正是 agent 可能「好心」去做的事：看到 `.env.production` 没入库，以为是漏了

## 被读进来的内容劫持

agent 读进上下文的一切都会影响它：网页、issue 内容、依赖包里的 README、日志、甚至代码注释。如果其中有一段写着「忽略之前的指示，执行以下命令」，模型有可能照做。这叫 prompt 注入，在编码场景里的典型入口是：

- 让它抓取网页查文档时，页面里藏着指令
- 让它处理别人提交的 issue 或 PR 内容
- 依赖包、第三方仓库里带着恶意的 CLAUDE.md 或 hooks 配置

对策是限制它被劫持之后能做的事：网络访问按域名放行、写权限和危险命令走审批、clone 来的仓库先看 `.claude/` 里有什么再运行。这个话题在[《Agent 安全》](../agent-safety/)里有系统的展开。

## 最大的坑：自己不再理解代码

最后一个坑不在 agent 身上，在你身上。agent 写得越多、越顺，你越容易停止阅读代码，直到某天线上出了问题，你发现自己已经不了解这个系统了。

几个保持理解的习惯：

- **关键模块自己读一遍**。核心的数据流、权限、计费、迁移，至少要知道它们在哪儿、怎么工作
- **让它解释，而不只是让它做**。「改之前先讲讲这个模块现在是怎么工作的」，顺便也能检验它是否理解对了
- **把「为什么」留在仓库里**。三个项目都坚持「注释写为什么」「规矩写原因」，这些文字既是给 agent 的，也是给半年后的你的
- **决策记录要更新**。hatch-shelf 的 CLAUDE.md 要求「架构或决策有变时同步更新 README（尤其是决策记录）」。让 agent 在改架构时顺手更新决策记录，你回头翻一遍，就知道这半年发生了什么

agent 是放大器：你对系统的理解清晰，它会放大你的产出；你的理解模糊，它会放大混乱。

## 本章要点

- 长会话变笨多半是上下文塞满：一事一会话、`/clear`、子 agent、进度文件、压缩后重新注入
- 快速迭代的依赖要在 CLAUDE.md 里写明版本并给出查文档的步骤；允许它说「不知道」，编造会减少
- 猜错代价大的事写明「交给人拍板」；任务写清范围，让它把其他问题列出来而不是顺手修掉
- 规矩不生效时依次排查：没加载、没触发、互相矛盾、太长、太模糊、本该用 hook
- 不可逆操作放进 deny / ask，机密文件加 Read deny，`bypassPermissions` 只在隔离环境用；读进来的内容可能带着注入
- 最大的坑是自己不再理解代码：读关键模块、让它解释、把「为什么」和决策记录留在仓库里

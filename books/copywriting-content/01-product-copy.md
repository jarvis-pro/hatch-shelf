# 产品文案

一人公司没有文案岗，也没有设计师替你挑词。按钮上写什么、页面叫什么、更新说明怎么写，最后都落到你手上，而且往往是在写代码的间隙顺手敲下去的。这一章讲界面里那些短句：它们为什么值得认真写、有哪些可以直接照用的规矩，以及怎么让一个人、一个 agent 在几十个页面里保持口径一致。

## 这本书讲什么、适合谁、怎么读

**讲什么**：「怎么写」。从界面里的一个按钮、一句报错，到着陆页、文章、个人主页，最后是怎么让 AI 帮你写又不像 AI 写的。渠道怎么选、在哪儿发、怎么做 SEO 和社区，是《获客与增长》的事，这里不重复。

**适合谁**：会写代码、不太会写字的独立开发者。你不缺表达能力，缺的是一套「写完能自查」的标准。

**怎么读**：

| 章节 | 解决的问题 | 什么时候读 |
|---|---|---|
| 1 产品文案 | 按钮、标题、术语、更新说明 | 做界面之前 |
| 2 报错、空态与确认框 | 出事时用户看到的那一句 | 写错误处理时 |
| 3 着陆页 | 别人第一次见到你的产品 | 上线前 |
| 4 内容营销 | 写一篇有人愿意读完的文章 | 开始做内容时 |
| 5 写作习惯 | 怎么持续写下去 | 任何时候 |
| 6 个人品牌 | 别人怎么记住你 | 开始公开露面时 |
| 7 用 AI 写但不像 AI | 让 agent 写初稿、你来定稿 | 已经在用 AI 写东西时 |

第 1、2 章和日常写代码关系最紧，建议先读；后面几章可以按需跳。

本书的案例主要来自两个项目：hatch-counter（产品名「掌柜眼」，给中小餐饮门店用的经营管理工具）和 hatch-shelf（本书架 App 本身）。掌柜眼的仓库规范里有一句话，几乎可以当作全书的纲：

> 面向店主写文案：报错、空态、确认框都是中文人话，说清后果。

## 为什么界面文案值得认真写

界面上能被看见的东西，大概只有三种：图形、数据、文字。图形和数据决定「看起来怎么样」，文字决定「用户知不知道该干什么」。

一个开发者写出来的界面，文字通常有三个毛病：

- **用开发者的词**：「同步失败」「会话过期」「记录不存在」。这些词在代码里准确，在用户那里是噪音
- **只说发生了什么，不说怎么办**：「操作失败」之后用户只能重试或者放弃
- **同一个东西有好几个名字**：这页叫「删除」，那页叫「移除」，第三页叫「清空」，用户会怀疑它们是三件不同的事

这些毛病的代价不会以报错的形式出现。用户不会提 issue 说「你这个按钮名字起得不好」，他只会犹豫、点错、找客服，或者默默不用了。对一人公司来说，**每一个本可以被文案挡住的客服问题，都是你的时间**。

## 四条基本规矩

### 用用户的词

先想清楚用户是谁，再决定用谁的词。掌柜眼的用户是餐馆店主，于是界面里写的是「补仓」「盘点」「进货单」「开支」，而不是「入库」「库存校准」「采购凭证」「费用」。

找用户的词有几个办法：

- 听用户自己怎么说：客服记录、访谈、他们发来的截图里手写的字
- 看他们手边的东西：收银小票、进货单、行业报表上印的是什么
- 看同行竞品，但只作参考，竞品也可能用错

一个容易忽略的细节：**用户的词可能「不准确」**。店主说「这道菜赚多少」，财务上应该叫毛利。界面标题可以写「赚了多少」，在解释的小字里再说清口径。准确留给说明，标题要先被看懂。

### 按钮写动作，而且写到底

按钮是「点下去会发生什么」的承诺。规矩是**动词 + 对象**，并且对象要具体：

| 常见写法 | 更好的写法 | 为什么 |
|---|---|---|
| 确定 | 删掉这一类 | 用户不用回头读弹窗正文就知道点下去的后果 |
| 提交 | 交单据 | 说的是这个业务里的那件事 |
| 保存 | 记一笔账 | 和页头按钮、空态里指路的叫法一致 |
| 下一步 | 去核对 | 告诉用户下一步是什么 |
| 是 / 否 | 挪过去再删掉 / 取消 | 两个选项各自是什么一眼可分 |

掌柜眼删除一个用过的开支分类时，确认按钮写的是「挪过去再删掉」，没用过的写「删掉」。同一个弹窗，按钮文字跟着后果变。这比统一写「确定」多写了几个字，换来的是用户不会误操作。

### 一个东西只有一个名字

列一张**叫法表**，写进仓库，人和 agent 都照着用。至少包括：

- 核心对象叫什么（书、章节、高亮；菜品、食材、单据）
- 核心动作叫什么（导入还是添加，删掉还是删除）
- 页面和导航叫什么
- 品牌名在哪儿用、仓库名在哪儿不能出现

掌柜眼的规范里有两条很典型：用户看得见的地方一律写品牌名「掌柜眼」，`hatch-counter` 只出现在仓库和包名里；侧边栏和页头标题一律四个汉字，改页名时要连指路文案、服务端报错里的页名一起搜一遍。后一条看起来是排版要求，实际是在保证「说到这个页面时，所有地方用的都是同一个名字」。

叫法表可以很简单：

```markdown
## 叫法表

| 概念 | 界面里写 | 不要写 | 备注 |
|---|---|---|---|
| 把书放进书架 | 导入 | 添加、上传 | 通道有 AirDrop、局域网、文件 App，结果都叫「导入」 |
| 去掉一本书 | 删除 | 移除、清除 | 确认框里要写清连带删掉什么 |
| 书里一段划线 | 高亮 | 标注、划线 | 高亮上可以附「笔记」 |
| 产品名 | 用户可见处写品牌名 | 仓库名 | 仓库名只在代码和路径里 |
```

把它放在 `CLAUDE.md` 或 `docs/` 里，让编码 agent 每次动界面时都能读到。比起事后一个个改，这是成本最低的做法。

### 指路指到能点的那一层

文案里经常要告诉用户「去哪儿做」。规矩是**指到用户能直接找到的那一层**，并且照原样写出界面上的名字。

掌柜眼的规范写得很具体：写「到「食材库存」补仓」，不要写「到库存管理补仓」，因为「库存管理」是一组七页，指过去不知道点哪一页；要连组一起写就写「员工管理 → 成员权限」。按钮在哪儿，照最窄的窗口写，因为宽屏在右上角的按钮，窄了可能折到别处。

这条规矩对文档、帮助中心同样适用。照着文档抄文案的人会把文档里的叫法抄回界面，源头错一处，下游错一片。

## 中文排版的几条硬规矩

中文界面里最常见的「不专业感」，往往不是用词，而是排版。下面几条可以当作检查清单：

| 规矩 | 错误示例 | 正确示例 |
|---|---|---|
| 中英文、中文与数字之间加空格 | 导入3本Markdown书 | 导入 3 本 Markdown 书 |
| 中文语境用全角标点 | 删除后无法恢复,确定吗? | 删除后无法恢复，确定吗？ |
| 数字和中文量词：项目内统一一种 | 同一屏里既有「3 天」又有「5个」 | 全项目都写「3 天」「5 个」 |
| 引用界面上的名字用直角引号 | 点击"记一笔账" | 点右上角「记一笔账」 |
| 书名用书名号 | 删除"Go 并发编程" | 删除《Go 并发编程》 |
| 不用感叹号表达普通结果 | 保存成功！ | 已保存 |

数字和中文单位之间加不加空格，各家规范不一样，**项目内统一**比选哪一种更重要。本书和掌柜眼都是「中英文之间加空格、引用界面名字用「」」。

这类规则适合交给工具检查，第 5 章会讲。

## 短，但不能短到丢信息

界面文案追求简短，但「短」的目标是减少阅读负担，不是减少字数。判断标准是：**删掉这几个字，用户会不会少知道一件他需要知道的事**。

- 「已删除」→ 够了，用户刚点了删除，知道删的是什么
- 「已删掉「肉类」」→ 在列表里一次能删很多项时，多出来的几个字有用
- 「已删掉「肉类」，原来记在它下面的挪进了「其他」」→ 删的时候发生了用户看不见的连带操作，必须说

第三句是掌柜眼真实的提示文案。它比「删除成功」长了很多，但每一个字都在回答用户可能会问的问题。

反过来，下面这些字通常可以删：

- 「请」「您」的堆叠：「请您点击此处进行登录」→「登录」
- 「进行」「操作」「相关」：「进行删除操作」→「删除」
- 主语明显时的「系统」「我们」：「系统已为您保存」→「已保存」
- 重复标题的正文：弹窗标题「删除书籍」，正文又写「您确定要删除这本书籍吗」

## 更新说明也是产品文案

App Store 的「新功能」、官网的更新日志、群里播的发版通知，读者都是用户。开发者写更新说明最常见的样子是：

```text
- 修复若干 bug
- 优化性能
- 重构导入模块
```

用户读完什么也没得到。掌柜眼的提交规范里有一条，直接解决了这个问题：提交信息**写改完之后是什么样，不写改了哪个文件**。它给的两个范例：

```text
feat: 后台员工管理能给别人重置密码：随机生成一串、只给看一次，旧密码和他所有的登录当场作废
fix: 配方管理跳下一道的快捷键按平台认：Mac 只认 ⌘↵，Windows 只认 Ctrl+↵
```

这两条提交信息几乎可以原样贴进更新日志：说了现在能做什么、边界在哪儿、和以前有什么不同。掌柜眼的 changelog 就是按路径从提交里收出来、发版时播进群里的，所以写提交信息本身就是在写给店主看的更新说明。只给开发者看的改动用 `chore:`，不进日志。

写更新说明的几条规矩：

1. **从用户的动作出发**：「导入时能看到每一章的检查结果」比「新增导入校验面板」好
2. **修复写现象**：「修复了横屏时目录被挡住的问题」比「修复 TOC 布局 bug」好
3. **重构、依赖升级不写**，除非用户能感知到变化（变快了、包变小了）
4. **有破坏性变化时放在最前面**，并写清用户要做什么

## 让文案集中、可检查

文案散落在几百个组件里，是叫法不一致的根源。几种集中方式各有适用场景：

| 方式 | 适合 | 代价 |
|---|---|---|
| 报错文案在服务端写，客户端原样展示 | 多端共享一套业务报错 | 服务端要有「给人看的话」和「给程序认的码」两个字段 |
| 一个 `copy.ts` 常量文件 | 单端、不做多语言 | 组件里多一层引用 |
| i18n 资源文件 | 要做多语言 | 引入一套库和工作流 |

掌柜眼选的是第一种：报错在服务端写，回包里同时带一句中文和一个机器码 `code`，客户端要区分处置时认 `code`、不认文案。这样同一件事只有一处文案，改了不会对不上。第 2 章会展开。

不做多语言的小项目，用一个常量文件就够了，再配一个简单的测试守住叫法表：

```ts
// src/copy/glossary.test.ts
import { readFileSync, readdirSync, statSync } from 'node:fs';
import { join } from 'node:path';
import { describe, expect, it } from 'vitest';

// 叫法表里「不要写」的那一列
const BANNED: Record<string, string> = {
  移除: '删除',
  添加书籍: '导入',
  标注: '高亮',
};

function walk(dir: string): string[] {
  return readdirSync(dir).flatMap((name) => {
    const p = join(dir, name);
    if (statSync(p).isDirectory()) return walk(p);
    return /\.(ts|tsx)$/.test(name) && !name.endsWith('.test.ts') ? [p] : [];
  });
}

describe('界面文案遵守叫法表', () => {
  it('没有出现禁用叫法', () => {
    const hits: string[] = [];
    for (const file of walk('src')) {
      const text = readFileSync(file, 'utf8');
      for (const [bad, good] of Object.entries(BANNED)) {
        if (text.includes(bad)) hits.push(`${file}: 「${bad}」应写作「${good}」`);
      }
    }
    expect(hits).toEqual([]);
  });
});
```

它很粗糙，会误伤注释，但足以在 agent 顺手写出「移除」时让测试变红。规则不在多，在于有人（或有测试）守着。

## 本章要点

- 界面文案的代价不以报错出现，而以犹豫、点错和客服问题出现；对一人公司来说就是时间
- 四条基本规矩：**用用户的词**、**按钮写动作并写到底**、**一个东西只有一个名字**、**指路指到能点的那一层**
- 把叫法表写进仓库，让人和 agent 都照着用；能用测试守住的就用测试守住
- 中文排版有几条硬规矩：中英文间空格、全角标点、界面名字用「」，项目内统一最重要
- 短的目标是减少阅读负担，不是减少字数；有用户看不见的连带后果时，必须写出来
- 更新说明写「改完之后是什么样」，提交信息写好了，更新日志几乎是现成的

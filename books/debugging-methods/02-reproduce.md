# 稳定复现

能稳定复现的问题，已经解决了一半。原因很简单：上一章的排查循环里，每个实验都要拿结果来判断假设，如果问题十次只出一次，那么「这次没出」什么也说明不了，可能是假设错了，也可能只是这次运气好。

这一章讲怎么把一个「偶尔出现」的问题变成「按这几步一定出现」的问题：先搞清楚复现需要哪些条件，再把复现的成本压低，最后把它固化成一个可以反复跑的脚本或测试。

## 复现需要的四类条件

一个问题出不出现，取决于四类条件。描述不了复现步骤，通常是漏了其中一类：

| 条件 | 例子 | 怎么收集 |
|---|---|---|
| 代码与版本 | App 版本、构建号、依赖版本、原生壳和 JS 包是否匹配 | 设置页显示版本号；日志里带上版本 |
| 数据 | 哪本书、哪个门店的账、哪首歌的来源 | 记下 id；能导出就导出一份 |
| 环境 | 设备型号、系统版本、网络、时区、语言、深浅色 | 截图时带上状态栏；日志开头记环境 |
| 时序与状态 | 前面做过什么操作、App 在后台多久、是否刚冷启动 | 操作记录、面包屑日志 |

前三类比较好收集，第四类最难，也最常是关键。「从书架进书正常，从搜索结果进书就白屏」「冷启动后第一次导入失败，之后都正常」，这类问题的复现步骤里必须写清楚**之前的路径**。

## 案例：一首歌放完了，进度还在往前跑

hatch-recordwall 是一个听歌的 App，曲库来自多个来源。有一段时间，偶尔会看到这样的现象：一首歌放完了，进度条没有停，时间显示变成 `5:22 / 5:06`，然后过一会儿这首歌又从头开始放，像是开了单曲循环。

「偶尔」是这个问题最大的障碍。下面是把它变成稳定复现的过程。

> [!NOTE]
> 两层根因和修复取自 hatch-recordwall 的真实提交 d7e445c；下面的出现记录、对照表和日志按提交信息重构，用来演示方法，不是原样。

### 第一步：收集出现时的条件

先不改代码，只在每次遇到时记一笔：

```text
11-02 21:10  B 站来源，单曲，放完后进度超出总长，然后从头重放
11-02 22:40  YouTube 来源，歌单最后一首，正常停住
11-03 08:15  B 站来源，歌单最后一首，进度超出总长
11-03 12:30  B 站来源，歌单中间，正常切到下一首（？）
```

四条记录就能看出模式：**出问题的都是 B 站来源，而且都是「队列里没有下一首」的时候**。歌单中间那一条正常，是因为有下一首可切，掩盖了问题。

### 第二步：提出假设，控制变量

两个变量：来源（B 站 / 其他）和队列位置（最后一首 / 中间）。各取两种，组合成四种情况分别试：

| 来源 | 队列位置 | 结果 |
|---|---|---|
| B 站 | 最后一首 | 进度超出总长，之后重放 |
| B 站 | 中间 | 切到下一首，但切换晚了几秒 |
| 其他 | 最后一首 | 正常停住 |
| 其他 | 中间 | 正常切换 |

「切换晚了几秒」是新发现：说明 B 站来源时，「播完了」这个信号本身就有问题，只是有下一首时被别的机制兜住了。

### 第三步：压低复现成本

每次复现都要等一首五分钟的歌放完，一个小时只能试十来次。压成本的办法：

- **直接拖到结尾**：seek 到总长前五秒再播放
- **找一首短的**：B 站上找一段一分钟以内的音频当固定测试数据
- **把测试数据固定下来**：记下这首歌的 id，写进开发笔记，以后都用它

压完之后，一次复现从五分钟变成十秒。这一步经常被跳过，但它决定了后面能做多少次实验。

### 第四步：在复现条件下观察

现在可以稳定复现了，加观测。在播放器的状态回调里打印每次回调的关键字段。下面的写法按 expo-audio 的类型定义核对过（`playbackStatusUpdate` 事件，状态里有 `currentTime`、`duration`、`playing`、`didJustFinish`）：

```typescript
player.addListener("playbackStatusUpdate", (s) => {
  console.log(
    `[player] t=${s.currentTime.toFixed(1)} d=${s.duration.toFixed(1)} ` +
      `playing=${s.playing} finished=${s.didJustFinish}`,
  );
});
```

B 站来源播到结尾时的日志：

```text
[player] t=304.1 d=306.2 playing=true finished=false
[player] t=305.6 d=306.2 playing=true finished=false
[player] t=307.0 d=306.2 playing=true finished=false
[player] t=308.4 d=306.2 playing=true finished=false
...
[player] t=322.3 d=306.2 playing=true finished=false
```

`didJustFinish` 从来没有变成 `true`，`currentTime` 一路涨过了 `duration`。B 站返回的是分段的 m4a，底层播放器播到头不报「结束」事件，时间却继续往前走。

这就是第一层根因：**收尾逻辑从来没有被触发**。

### 第五步：修第一层，发现第二层

补上一道兜底：`didJustFinish` 或者 `currentTime >= duration` 谁先到算谁的，并把显示的进度夹在总长以内。再跑复现：进度不再超出了，但歌还是会从头重放。

继续观察。原来的代码在队列到头时只改了 store 里的状态，播放器本身还在 playing，于是补了一个 `pause()`。仍然重放。再看日志，发现收尾时为了把进度归位做了一次 seek，而 **seek 会把播放器从「结束」拉回「在播」**，只停一次的话这首歌会自己从头再放。在 seek 之后再停一次，才真正停住。

这个案例里有两个叠在一起的问题。如果没有稳定复现，修完第一层之后看到「好像好了一些」，很可能就收工了。

## 最小复现

复现步骤稳定之后，下一步是让它**更小**：去掉一切与问题无关的部分，直到剩下的每一样东西都是必需的。

最小化的方法就是逐个删：

1. 从完整的复现开始
2. 删掉一部分（一个组件、一段数据、一个配置项）
3. 问题还在：这部分无关，真的删掉
4. 问题消失：这部分相关，放回去，并记下来
5. 重复，直到删不动

举一个示例场景（不是真实发生过的故障）：假设 hatch-shelf 的阅读器在一章两万字的 Markdown 里某处排版错乱。先把章节一半一半地删，几轮之后剩下三行：一个列表项里嵌了一个代码块，代码块里有一个 `$`。这三行就是最小复现，看着它们很容易想到是公式插件的行内规则和代码块规则在抢同一个 `$`，和那两万字的其他部分无关。

最小复现的价值在于：

- **根因常常自己显现**：剩下三行时，你几乎能直接看出是哪两个规则在打架
- **可以写成测试**：三行 Markdown 很适合放进单元测试，防止回归
- **可以拿去问人**：给上游库提 issue、问同事、交给编码 agent，三行比两万字有用得多

## 让偶发问题变频繁

有些问题本质上就是概率性的：竞态条件、超时、内存压力下才出现的问题。这时候目标不是「每次必现」，而是「把概率提高到可以做实验的程度」。

### 放大时序问题

竞态的本质是两件事的先后顺序不确定。放大它的办法是**人为拉开或压缩时间差**：

- 在可疑的异步步骤前后加 `await sleep(500)`，看问题是变多了还是消失了。变多说明你找对了竞争的那一段
- 用 Chrome DevTools 的 Network 面板把网络限速到慢速，让请求晚回来
- 用 DevTools 的 Performance 面板给 CPU 降速，让 JS 执行变慢

第 1 章 book.yaml 的问题，如果当时复现不稳定，在 `tmp.move` 前加一个 `sleep` 就能让问题消失，这本身就是证明时序假设的实验。

### 循环跑

把复现写成脚本，跑一百次，统计失败次数：

```bash
fails=0
for i in $(seq 1 100); do
  pnpm vitest run tests/import.test.ts > /dev/null 2>&1 || fails=$((fails + 1))
done
echo "failed $fails / 100"
```

这个数字本身就是实验结果。改动前 100 次失败 7 次，改动后 100 次失败 0 次，比「我试了几次没出现」可信得多。如果改动前后都是 7 次左右，说明这个改动没碰到根因。

### 加压

内存、并发、数据量相关的问题，在开发机上常常不出现，因为开发机太宽裕了：

- **数据量**：hatch-shelf 用一百本书的书库测试，而不是三本示例书
- **并发**：hatch-counter 用 k6 或一个简单的 `Promise.all` 同时发 50 个请求
- **资源**：Docker 里限制容器的内存 `--memory=256m`，模拟线上的小机器
- **设备**：在最老的那台测试机上跑，而不是最新的 Mac

## 不稳定的测试也是问题

CI 里偶尔失败、重跑就过的测试，常被当成「测试的问题」直接重跑了事。但它通常说明两件事之一：测试本身依赖了时序或全局状态；或者被测代码真有竞态，只是线上还没撞上。

排查不稳定测试的步骤和排查偶发 bug 一样：

1. 用循环跑统计失败率
2. 单独跑这一个测试，看失败率变不变。变低了说明它受别的测试影响（共享的数据库数据、全局 mock、模块级状态）
3. 打乱顺序跑，Vitest 支持 `--sequence.shuffle`，看失败是否和顺序有关
4. 找到之后修根因，而不是加 `retry`

> [!WARNING]
> Vitest 的命令行参数在不同大版本间有过调整，`--sequence.shuffle` 等写法以 vitest.dev 上当前版本的 CLI 文档为准。

## 在干净的环境里复现

有时候问题只在你自己的开发机上出现，或者只在你的机器上不出现。原因常常是环境里残留的东西：旧的缓存、手动改过的配置、某个全局安装的工具。在一个干净的环境里复现，可以把这些排除掉：

- **干净的代码**：用 `git worktree add /private/tmp/clean main` 拉一份全新的检出，在里面 `pnpm install` 再跑，不受当前工作区未提交改动的影响
- **干净的缓存**：Metro 用 `npx expo start --clear` 清掉打包缓存；Vite 删 `node_modules/.vite`；浏览器用无痕窗口
- **干净的设备状态**：模拟器里删掉 App 重装，或者新建一个模拟器；这样能复现「新用户第一次打开」的问题
- **干净的数据**：用种子数据重建一个空的数据库，而不是用开发时积累下来的那份

反过来也成立：如果问题在干净环境里**不出现**，那么差异就在你的环境里，可以对环境做二分（下一章）。

## 写下复现步骤

复现成功后，把步骤写成别人照着做就能复现的形式。一个好的复现步骤长这样：

```text
环境：recordwall iOS dev client，iPhone 15 模拟器，iOS 18
数据：B 站来源的测试曲目 id=bv-xxxx（时长 1:04）
步骤：
  1. 清空播放队列
  2. 只把这一首加入队列并播放
  3. 拖到 0:58
期望：播到 1:04 停住，进度显示 1:04 / 1:04
实际：进度继续增长到 1:20 左右，随后从 0:00 重新播放
频率：10/10
```

注意「期望」和「实际」分开写，「频率」写成分数。这份步骤可以直接放进 issue、排查记录，或者作为提示词的一部分交给编码 agent。

## 实在复现不了怎么办

有些问题在开发环境里无论如何都复现不了，比如只在某个用户的设备上、只在线上的流量下出现。这时候的策略要换成「**让它下次出现时留下足够的证据**」：加日志、加上报、加看门狗。这是[第 9 章](09-production-only.md)的主题。

在走到那一步之前，先确认几件事：

- 线上和本地的**构建方式**一样吗？Release 和 Debug 构建在代码压缩、Hermes 字节码、`__DEV__` 分支上都不同
- **数据**一样吗？能不能把出问题的那份数据导出来，在本地导入
- **配置**一样吗？环境变量、功能开关、服务端下发的配置

很多「线上才有」的问题，换成 Release 构建或者导入线上那份数据后，本地就能复现了。

## 本章要点

- 复现不稳定时，实验结果没有说服力；先解决复现，再做实验
- 复现条件分四类：代码版本、数据、环境、时序与状态；第四类最常被漏掉
- 记录每次出现时的条件，几条记录就能看出模式；然后控制变量逐个验证
- 压低复现成本（拖到结尾、用短的测试数据），决定了能做多少次实验
- 最小复现：逐个删，直到删不动；根因常常自己显现，还能直接写成测试
- 偶发问题用加延迟、限速、循环跑、加压来提高概率，用失败率做实验结果
- 不稳定的测试也是 bug，查根因而不是加重试

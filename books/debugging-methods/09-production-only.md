# 线上无法复现的问题

前面几章的方法都有一个前提：你能在自己手边让问题出现。但总有一些问题，用户那里一直出，你这里怎么也复现不了。它们往往是最难的问题，也往往是最影响用户的问题。

面对这类问题，策略要从「复现它」转成「**让它下次出现时留下足够的证据**」。这一章讲为什么有些问题只在线上出现、怎么设计能留下证据的观测、怎么在证据有限的情况下推进假设，以及怎么做「即使没完全弄清根因也能兜住」的修复。

## 为什么只在线上出现

线上和开发环境的差异，大致可以归为几类。拿到一个「复现不了」的问题，先对照着想一遍：

| 差异 | 例子 |
|---|---|
| 时长 | 开发时 App 开几分钟，用户开一整天；服务跑了三天才出问题 |
| 规模 | 开发时 3 本书，用户 300 本；测试库 10 行，线上 10 万行 |
| 设备和系统 | 用户的手机更老、系统版本不同、存储快满了 |
| 网络 | 用户在地铁里、Wi-Fi 和蜂窝之间切换、在公司代理后面 |
| 生命周期 | App 进后台、锁屏、被系统挂起、被杀掉后恢复 |
| 构建 | Release 构建：压缩、Hermes 字节码、没有 `__DEV__` 分支 |
| 并发 | 线上多个用户同时操作同一份数据 |
| 时间 | 时区、夏令时、月底、闰年、跨年 |

开发时的使用方式很「干净」：App 在前台、网络稳定、每次都是新启动。用户的使用方式恰恰相反。很多「复现不了」的问题，只要按上表模拟出对应的条件，就能复现。

## 案例：连播停在半路

> [!NOTE]
> 根因和修复思路取自 hatch-recordwall 的真实提交 5c1e3bb；下面的排查经过、环形日志代码、日志样例和看门狗代码按提交信息重构，用来演示方法，不是原样。

### 现象

hatch-recordwall 可以连续播放一整张专辑或歌单。用户（也就是开发者自己，日常通勤时用）反馈：有时候连播到一半就停了，进度条不动，按播放、暂停、下一首都没有反应，只能把 App 彻底关掉重开。

坐在桌前调试时，怎么放都正常。

### 第一轮：对照差异

对照上面那张表，坐在桌前和通勤时的差异：

- **生命周期**：通勤时手机锁屏放在口袋里，App 在后台；桌前时 App 在前台
- **网络**：通勤时会在 Wi-Fi、蜂窝之间切换；桌前一直是 Wi-Fi
- **时长**：通勤时一次连放四五十分钟；调试时一般听一两首

三个候选，但都只是猜测，没有证据。这时候不急着修，先加观测。

### 第二轮：让问题留下证据

App 里本来就有日志，但都是 `console.log`，只在连着开发工具时才看得到。加了一个**环形缓冲日志**：在内存里保留最近两千条，每隔一段时间和进入后台时写到文件，设置页里加一个「导出诊断日志」按钮，通过系统分享面板导出。

```typescript
const MAX = 2000;
const buffer: string[] = [];

export function trace(tag: string, data?: Record<string, unknown>) {
  const line = `${new Date().toISOString()} ${tag}${data ? " " + JSON.stringify(data) : ""}`;
  buffer.push(line);
  if (buffer.length > MAX) buffer.shift();
}

export function flushTrace() {
  traceFile.write(buffer.join("\n"));
}
```

然后在关键位置打点：App 前后台切换、网络类型变化、播放器每一次状态回调、取播放地址的开始和结束、切歌、所有错误。

这样做的原则是：**记录状态的变化，而不是只记录错误**。问题恰恰可能是「没有报错」。

### 第三轮：读证据

又通勤了两天，遇到一次停播，导出日志。关键的一段：

```text
08:14:02.115 app.state background
08:31:47.902 net.change {"from":"wifi","to":"cellular"}
08:33:10.441 track.end {"id":"a7","by":"didJustFinish"}
08:33:10.452 resolve.start {"id":"a8"}
08:33:40.453 resolve.timeout {"id":"a8","ms":30000}
08:33:40.460 track.skip {"id":"a8"}
08:33:40.461 resolve.start {"id":"a9"}
...
08:41:05.120 player.status {"state":"readyToPlay","playing":true,"t":12.4}
08:41:05.620 player.status {"state":"readyToPlay","playing":true,"t":12.4}
08:41:06.120 player.status {"state":"readyToPlay","playing":true,"t":12.4}
08:41:06.330 player.error {"code":403}
```

日志里能读出两个问题：

1. **切歌时取下一首的地址超时了**。取播放地址需要在一个隐藏的 WebView 里完成签名，而 App 进入后台几十秒后，WebView 里的 JS 就被系统挂起了。在曲末、App 在后台时现场签名，是在最不可能成功的时候做最容易失败的事
2. **流已经 403 了，播放器状态却一直是 `readyToPlay`**。网络从 Wi-Fi 切到蜂窝后，播放地址失效（地址绑定了请求时的出口 IP）。播放器自身的状态不反映这条流的失败，错误只出现在单独的 error 字段里。而原来的「断了自动重取」逻辑是看播放状态的，于是从来没有触发过

第二点还解释了「按什么都没反应」：在播放器看来它一直在正常播放，按暂停再播放，它就继续在那条死掉的流上「播放」。

这两个根因，在桌前调试时都不会出现：App 在前台，WebView 没被挂起；网络不切换，地址不失效。

### 修复：既修根因，也加兜底

针对已经确认的根因：

- **按错误字段判断流是否失效**，而不是按播放状态；失效时重新取地址，从原来的位置接着播
- **提前取下一首**：播到 40% 时就取好下一首的地址并预加载。省下一两秒等待是次要的，主要是把签名挪回 App 还在前台的时候
- **重取时绕开缓存**：失效的地址离过期时间还早，读缓存等于把同一条死地址再交出去一遍

针对「卡法一种一种去猜是猜不完的」，加了一条兜底：

- **看门狗**：如果「希望在播放」并且「播放位置 12 秒没有前进」，就重取地址、接回原位。它不关心卡住的原因是什么，只认「声音没有往前走」这一件事

```typescript
let lastPos = -1;
let stalledSince = 0;

setInterval(() => {
  if (!state.wantPlaying) {
    stalledSince = 0;
    return;
  }
  const pos = player.currentTime;
  if (pos !== lastPos) {
    lastPos = pos;
    stalledSince = 0;
    return;
  }
  stalledSince ||= Date.now();
  if (Date.now() - stalledSince > 12_000) {
    trace("watchdog.recover", { id: state.current?.id, pos });
    stalledSince = 0;
    void recover({ bypassCache: true, resumeAt: pos });
  }
}, 1_000);
```

还有一个细节：播放器的周期状态回调只在真的在播放时才发出，卡住时恰恰一条都不来。所以看门狗不能依赖状态回调，要自己定时去问当前位置。

界面上也跟着改：把「希望在播放」和「真的在出声」分开，缓冲、重连时页头显示「正在换片」「在等数据」「断了，正在接回来」，不再显示成一个能按却没反应的播放键。

### 验证

线上问题的修复，验证也要在线上条件下做：

1. 用模拟的方式先验证兜底逻辑：开发时手动把当前播放地址改成一个会 403 的地址，看是否能接回
2. 模拟后台：播放中锁屏，等几分钟，看下一首能否正常接上
3. 实际通勤使用一周，导出日志，搜索 `watchdog.recover` 和 `resolve.timeout` 出现的次数和之后是否正常接回

看门狗每次触发都记一条日志，这一点很重要：**兜底逻辑会掩盖问题**。如果它触发得很频繁，说明还有没找到的根因，只是被兜住了。

## 设计能留下证据的观测

上面的案例里，真正的突破点是那份诊断日志。线上问题的排查能力，很大程度上取决于**问题发生之前**你埋了什么。

### 记什么

- **状态变化**：前后台、网络、登录状态、播放状态、连接状态
- **边界上的进出**：每个外部调用的开始、结束、耗时、结果
- **关键决策**：走了哪个分支、为什么跳过、为什么重试
- **环境信息**：App 版本、构建号、系统版本、设备型号，在日志开头记一次

### 怎么拿回来

不同的产品形态有不同的方法：

| 形态 | 方法 |
|---|---|
| 服务端 | 结构化日志集中收集，按请求 id 检索；错误监控 |
| 网页、Electron | 错误监控 SDK 上报；或者应用内「导出诊断信息」 |
| 联网的 App | 错误监控 SDK、面包屑 |
| 不联网的 App | 本地环形日志加系统分享导出 |

hatch-shelf 的设计原则是 App 不联网，不能接错误监控服务。所以它和上面的 recordwall 用一样的办法：日志留在本地，需要时用户主动导出。这种方式的好处是用户完全知道导出了什么。

错误监控服务的接入方法见[《可观测性与性能》的错误监控一章](../observability-performance/05-error-monitoring.md)。

### 注意隐私

诊断日志要能拿给别人看（包括交给编码 agent），所以：

- 不记录用户的内容：书的正文、账目的金额明细、手机号
- id 可以记，名字尽量不记
- 导出前让用户看到导出的内容，或至少说明包含什么

## 向用户问清楚

线上问题的第一手信息常常来自用户的一句话：「用着用着就不动了」。这句话本身信息很少，但用户手里有你需要的全部条件。问的时候用具体的问题，而不是「能详细描述一下吗」：

- 最后一次正常是什么时候，之后做了什么
- 当时在什么网络下，App 在前台还是刚从后台切回来
- 能不能截一张图，截图里带上状态栏（有时间、网络、电量）
- 重启 App 之后还会不会出现
- 最近有没有更新 App 或系统

对 hatch-counter 这种面向店主的产品，可以在错误提示里直接显示一个简短的错误编号（请求 id 的前几位），让用户截图时自然就带上了。拿到编号就能在日志里找到那次请求，省掉大半的来回询问。

## 在线上安全地做实验

有时候需要在线上验证一个假设。几种相对安全的方式：

- **只加观测，不改行为**：多打一些日志、多记一些指标，这类改动风险最低
- **功能开关**：新的处理逻辑放在开关后面，先只对自己的账号或一家门店打开
- **灰度**：先发给一部分用户。移动端可以先发 TestFlight 给自己和少数用户
- **影子执行**：新旧两种逻辑都跑，只用旧逻辑的结果，对比两者的差异并记录

hatch-counter 的服务端问题，常用的做法是先在日志里加上能区分假设的字段，部署，等一天，再按字段统计。比如怀疑某个慢接口只在某几家数据量大的门店上慢，就在接口日志里加上门店的数据量，一天后按数据量分组看耗时。

## 用线上数据在本地复现

很多线上问题的差异在**数据**。能把出问题的那份数据拿到本地，往往就能复现：

- hatch-shelf：让用户把出问题的书通过分享导出，本地导入
- hatch-counter：从备份恢复一份数据库到本地，或者只导出出问题那家门店的数据

> [!CAUTION]
> 线上数据包含真实用户的信息。拿到本地前先脱敏（手机号、姓名、金额），用完删除；不要把线上数据提交进仓库，也不要原样贴给外部服务。

## 本章要点

- 线上才出现的问题，通常源于时长、规模、设备、网络、生命周期、构建、并发、时间的差异；先对照着模拟
- 复现不了时，策略转成让问题下次出现时留下证据：记录状态变化，而不只是错误
- 不联网的 App 用本地环形日志加系统分享导出
- recordwall 停播：后台时 WebView 被挂起导致取地址超时；网络切换后流 403，但播放器状态不反映
- 修复既修确认的根因，也加只认结果的兜底（看门狗）；兜底要记日志，否则会掩盖新问题
- 线上实验从只加观测开始，再用功能开关、灰度、影子执行
- 线上数据拿到本地前先脱敏

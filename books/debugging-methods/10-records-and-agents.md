# 排查记录与经验沉淀

一次排查结束时，你脑子里有很多东西：排除过哪些假设、哪个工具在这种情况下最好用、根因是怎么一步步浮现的。如果什么都不留下，三个月后遇到类似的问题，你会从头再走一遍；更糟的是，同一个根因可能在别处再出现一次。

这最后一章讲怎么把排查过程和结论留下来：排查中的工作记录、结束后的提交信息和复盘、把教训变成能自动拦截问题的规则。最后讲一个越来越常见的场景：让编码 agent 协助排查，以及怎样让它真正帮上忙而不是添乱。

## 排查中：工作记录

第 1 章说过，每做一个实验记一行。这里给一个可以直接用的模板，一个纯文本或 Markdown 文件就够。下面用第 9 章的例子填了一份，版本号、设备等内容是示例：

```markdown
# 连播停在半路

## 现象
- 连播中途停止，进度不动，按键无反应，只能杀掉重开
- 通勤时出现，桌前调试从未出现
- 版本：recordwall 0.9.2 (iOS)，iPhone 13，iOS 26

## 已知 / 已排除
- [x] 与具体歌曲无关（三次停在不同来源的歌上）
- [x] 不是内存问题（停播时内存平稳）

## 假设与实验
- H1 后台时取地址失败
  - 实验：加环形日志，记录取地址的开始、结束、耗时
  - 结果：后台时 resolve.timeout，30 秒
  - 结论：站住，但只解释了一部分（为什么按键也没反应？）
- H2 流失效后播放器不报错
  - 实验：日志记录 player.status 和 player.error
  - 结果：403 后 state 仍为 readyToPlay
  - 结论：站住

## 根因
...

## 修复与验证
...

## 遗留
- 看门狗触发次数一周后再看一次
```

几个要点：

- **「已排除」单独一节**：这是最有价值的部分，能防止自己和别人绕回去
- **结论写「站住」「推翻」「不确定」**，不写「好像」
- **遗留问题写下来**：修复后还没想通的地方、需要后续观察的指标
- **记录写在仓库外或者专门的目录里**，不要和代码混在一起；结束后把有价值的部分提炼出去

## 排查后：提交信息就是最好的记录

修复的提交信息是最容易被找到的记录：以后有人对着这段代码 `git blame`，第一个看到的就是它。一个好的修复提交信息回答三个问题：**现象是什么、根因是什么、为什么这样修**。

对比两种写法：

```text
fix: 修复播放问题
```

```text
fix: 一首放完之后真的停住，进度不再自己往前跑

两层问题叠在一起：

一是收尾根本没被触发。didJustFinish 是正路，但 B 站那种分段 m4a 播到头之后
AVPlayer 不报它，currentTime 还会一路涨过 duration。改成再按时长兜一道，
两者谁先到算谁的；顺手把显示出来的进度夹在总长以内。

二是就算触发了也停不住。队列到头只改了 store 里的状态，播放器还在 playing；
补上 pause 之后又发现，播到头那次 seek 会把播放器从「结束」拉回「在播」，
只停一次的话这一首会自己从头再放。seek 之后再停一次才真的停下。
```

第二种写法是 hatch-recordwall 的真实提交（第 2 章的案例）。它的价值在于：将来有人看到「seek 之后又 pause 了一次」觉得多余想删掉时，提交信息会告诉他为什么不能删。

除了提交信息，**代码注释**也要写「为什么」：

```typescript
// SDK 58 起 write() 是异步的；必须同步写完，下面的 rename 才不会抢在写入之前
file.writeSync(f.bytes);
```

这行注释防止的是一次「顺手优化」导致的回归。

## 复盘：一个人也值得做

团队里的复盘（postmortem）有一套完整的流程，见[《一人运维手册》的复盘一章](../production-ops/04-postmortem.md)。一个人的项目不需要那么正式，但遇到以下情况值得花十分钟写一段：

- 排查花了超过半天
- 影响了用户（数据错了、服务停了）
- 根因出乎意料
- 同类问题出现了第二次

一个人的复盘只需要回答四个问题：

1. **发生了什么**：一两句话
2. **为什么花了这么久**：哪一步走了弯路，当时缺了什么信息
3. **同一个根因还可能在哪里**：搜一遍代码
4. **怎么让它不再发生，或者下次更快被发现**：这是最重要的一条，下一节展开

第 2 条特别有价值。回顾这本书里的案例，走弯路的原因大多是同一类：凭直觉先查了「看起来可疑」的地方（第 6 章的 SQLite）、忽略了已经出现的警告（第 7 章的 `MaxListenersExceededWarning`）、在复杂的客户端里找而不是先用简单的客户端排除（第 8 章的手机 Safari）。把这些写下来，下次会快很多。

## 把教训变成规则

记录是给人看的，人会忘。更可靠的是**把教训变成机器会检查的规则**。从轻到重：

| 形式 | 例子 | 防住什么 |
|---|---|---|
| 回归测试 | 开支合计等于明细之和，覆盖不能整除的金额 | 同一个 bug 再次出现 |
| lint 规则 | `no-floating-promises`，不许用 `eslint-disable` 绕过 | 没有 await 的 Promise（第 1 章） |
| 类型约束 | preload 的订阅接口类型签名必须返回 `() => void` | 订阅没有取消（第 7 章） |
| 发版前检查 | 发版时不许用环境变量覆盖曲库地址 | 调试配置被带进正式版（第 8 章） |
| 项目约定 | 金额一律用整数分存储和计算 | 浮点舍入误差（第 3 章） |
| agent 规则 | 写进 `CLAUDE.md` 或按路径生效的规则文件 | agent 写出同类问题 |

hatch-recordwall 的 iOS 发版脚本里有一道拦截（提交 4d2fc03）：真机调试时用来把曲库地址指向局域网的环境变量，如果发版时还在，脚本直接报错退出。这类检查写起来只要几行，但它把「希望下次记得」变成了「下次不可能忘」。

hatch-counter 修重复提交（第 8 章，提交 2d685aed）时，同一个提交里也改了桌面端的规则文件 `.claude/rules/desktop-ui.md`：会落账的主按钮必须走统一的提交封装，重试沿用同一个请求号。规则写在这里，人和 agent 以后写新按钮时都会读到。

## 症状索引

经验多了之后，有一份「症状 → 可能的根因」索引会很有用。它不需要完整，只记那些曾经花了很长时间、而症状又有辨识度的：

| 症状 | 先查什么 |
|---|---|
| 报错的文件名、位置每次不同 | 时序问题，有没有没 await 的异步操作 |
| 只在真机上连不上 | 服务监听的地址、明文 HTTP 限制、本地网络权限 |
| 越用越慢，重开就好 | 泄漏，先看有没有累积的监听器 |
| 切到某个页面时动画顿一下 | JS 线程上的同步重计算 |
| 改了没生效 | 缓存、构建产物、没重启的进程、没重新构建的 dev client |
| 用户输入导致 500 | 校验漏了，数据库错误码没有映射成 4xx |
| 只在后台久了之后出问题 | WebView 被挂起、网络被限制、进程被回收 |

这份表最好放在你每天都会看到的地方，比如项目的开发文档里。

## 让编码 agent 协助排查

编码 agent 在排查中能帮上很大的忙，但用法和让它写功能不太一样。它的工作方式和局限见[《编码 Agent 实战》](../coding-agents/)，这里只讲排查场景。

### 它擅长什么

- **读大量文本**：几千行的日志、一个大文件的历史改动，它能很快找出模式
- **搜代码**：同一个根因还可能出现在哪里，它可以一次搜遍整个仓库
- **写一次性工具**：bisect 的判断脚本、复现脚本、日志分析脚本
- **提出候选假设**：根据现象和代码列出可能的原因，有时能想到你没想到的
- **执行实验**：加日志、跑测试、对比结果

### 它容易犯什么错

- **直接修症状**：看到「提示条重复弹出」就加一个防抖，看到报错就包一层 `try/catch`，看到警告就调大 `setMaxListeners`
- **一次改很多处**：同时改五个地方，问题没了，但不知道是哪一处起的作用
- **过早宣布成功**：测试通过了就说修好了，但没有回到原始现象去验证
- **对着错误的假设一路走下去**：你在提示词里带了一个假设，它倾向于去证实它

这些和第 1 章说的人的问题一模一样，所以对策也一样：**用排查循环约束它**。

### 案例：传书时提示条反复弹出

> [!NOTE]
> 问题和修复代码取自 hatch-shelf 的真实提交 011bc52；下面和 agent 的两轮对话是示例场景，用来演示提示词的写法，不是原样记录。

hatch-shelf 的传书页面在接收文件时会弹一个提示条，几秒后自动收起。有一次发现：一次传很多文件时，提示条会反复从头弹出，像是在闪。

第一次的提示词很随意：

```text
传书页面接收文件时，顶部提示条会反复弹出，修一下
```

agent 给出的修复是给提示条加了一个「500 毫秒内不重复显示」的节流。现象确实没了，但这是修症状：提示条为什么会重复弹出，仍然不知道。

撤销这个改动，换一种问法：

```text
传书页面接收文件时，顶部提示条会反复从头弹出。
复现：电脑上一次拖入 20 个文件上传，观察手机上的提示条。

先不要改代码。请：
1. 读 app/src/app/(tabs)/transfer.tsx 里提示条的实现
2. 列出可能导致它重复播放进场动画的原因，每条说明怎么验证
3. 按可能性排序

只有在我确认根因之后再修改。
```

agent 读完代码后给出的第一个假设是：提示条组件的 `useEffect` 依赖数组里有 `onHide`，而 `onHide` 是父组件每次渲染都会新建的函数；上传进度每次刷新都会让父组件重新渲染，effect 就重新执行一次，动画从头开始。

验证方法也是它建议的：在 effect 里加一行日志，上传时看它执行了多少次。结果是上传过程中执行了几十次，假设站住。

修复是把 `onHide` 从依赖里拿出来，用 `useEffectEvent` 包一层，让 effect 能读到最新的回调而不因为它变化而重跑：

```tsx
// onHide 每次渲染都是新函数，不能放进依赖，否则上传进度一刷新提示就从头再弹一次
const hide = useEffectEvent(onHide);

useEffect(() => {
  // ...进场动画
  anim.start(({ finished }) => finished && hide());
}, [item, v]);
```

> [!WARNING]
> `useEffectEvent` 在 React 19.2 起成为稳定 API，之前的版本只在实验通道提供。以 react.dev 对应版本的文档为准。

同一次排查里还顺带发现进度条的另一个问题：换到下一个文件时，进度条会从上一个文件的进度倒退回去，而不是从 0 开始。这也是因为组件被复用了，修法是换文件时给进度条一个新的 `key` 让它重新挂载。

### 给 agent 的排查提示词

从这个案例可以总结出一个结构：

```text
现象：<报错原文、截图描述、期望与实际>
复现：<稳定的复现步骤，或者「复现不了，只有这份日志」>
已排除：<已经验证过不是的原因>
相关文件：<你知道的入口>

先不要修改代码。请先读代码并列出候选原因，每条给出验证方法。
验证时一次只改一处，并告诉我结果。
确认根因后，先写一个能复现问题的失败测试，再修复。
修复后回到原始复现步骤验证，而不只是跑测试。
```

几个要点：

- **「先不要修改代码」**：把它从「修复者」切换到「调查者」
- **给「已排除」**：省掉它重复验证你已经做过的事
- **不在提示词里塞你的假设**：除非你很确定。如果你写了「我觉得是缓存的问题」，它会花很大力气去证明是缓存的问题
- **要求失败测试先行**：这是区分修根因和修症状最有效的手段
- **要求回到原始现象验证**

### 数据和安全

把日志、错误信息交给 agent 之前，确认里面没有密钥、令牌、用户的个人信息。第 9 章说的诊断日志「不记录用户内容」，在这里也派上了用场。线上数据库的连接串、生产环境的 SSH 权限，不要直接交给 agent 去操作，见[《Agent 安全》](../agent-safety/)。

## 本书回顾

这本书的方法可以浓缩成几句话：

- 排查是一系列小实验：观察、假设、实验、记录
- 先让问题稳定复现，复现不了就让它留下证据
- 没有头绪时二分，它不需要你猜对
- 逐字读日志和堆栈，第一条错误最重要
- 用调试器看「本该发生却没发生」的事
- 性能和内存问题先变成数字，再用火焰图和堆快照找到具体的位置
- 跨端问题分层切开，用最简单的客户端排除一大块
- 修复先写失败的测试，再找同一根因的其他位置，最后把教训变成规则

方法本身不难，难的是在压力下仍然按方法做。这也是为什么要记录：记录会提醒你现在在循环的哪一步。

## 本章要点

- 排查中用一份工作记录，「已排除」单独一节，结论只写站住、推翻、不确定
- 修复的提交信息写清现象、根因、为什么这样修；代码注释写「为什么」
- 一个人也值得做简短复盘，重点是为什么花了这么久、怎么让下次更快
- 把教训变成机器会检查的规则：回归测试、lint、类型、发版前检查、agent 规则
- 维护一份症状到根因的索引
- 让 agent 协助排查时，先让它当调查者而不是修复者：给现象、复现、已排除，要求列假设和验证方法、失败测试先行、回到原始现象验证
- 交给 agent 的日志和数据先去掉密钥和个人信息

# 阶段 0：盘点与准备

阶段 0 不产出任何对外的东西。它要做的是把几件「大概知道」的事变成写下来的数字和结论：你需要多少收入、每周真正有多少时间、副业的边界在哪、手里已经有什么、现在到底处在哪个阶段。

很多人跳过这一步，直接开始写代码或者找客户。后果通常在几个月后才出现：发现每周根本挤不出十小时，发现劳动合同里有兼职报备条款，发现做了半年还说不清「做到什么程度可以辞职」。阶段 0 用两到四周把这些事一次理清，后面每个阶段都会用到这里的结果。

## 进入条件与周期

- **进入条件**：有一个想做的方向，或者已经有一个在做的产品。方向怎么选不在本书范围，见[《一人公司方法论》第 2 章](../opc-playbook/02-choosing-direction.md)
- **周期**：2–4 周，每周 10 小时左右。这个阶段不需要整块时间，适合在工作日晚上分几次做

## 第 1 周：算出你的数字

### 最低可行收入

最低可行收入是让你不必回去打工所需的每月税后净收入，算法见[《一人公司方法论》第 1 章](../opc-playbook/01-what-is-opc.md)「一人公司的目标函数」。这里补几条实操上容易漏的：

- **用过去 6–12 个月的真实账单算**，不要凭印象估。把支付宝、微信、银行卡的账单导出来，按类别加总。凭印象估的开支通常偏低
- **把现在由单位承担的东西列出来**：单位缴的那部分社保和公积金、补充医疗、餐补、交通补贴、公司配的电脑和软件。辞职后这些要么自己出，要么没了
- **社保医保按自己缴的口径估**：以灵活就业人员身份缴纳的费用怎么算，各地不同，以当地社保经办机构的最新规定为准。离职后的社保安排见[《过渡期收入与个人保障》](../opc-transition/)
- **一年一次的大额开支摊到月**：保险、年费、过节、回老家

写下来的结果放进 `plan/numbers.md`：

```text
# 我的数字（2026-11 版）

最低可行收入 M（税后，每月）：____ 元
  其中 必要生活开支：____
       自缴社保医保（估）：____
       经营成本（服务器、域名、模型调用、代账）：____
       储蓄余量：____
现在每月税后工资：____ 元
可动用储蓄（已扣应急金）：____ 元
应急金（留着不动）：____ 元，按 __ 个月开支
静态跑道 = 可动用储蓄 ÷ M = ____ 个月
下次更新：____（每季度一次，或开支变化时）
```

### 产品要算到的数

再用《一人公司方法论》第 2 章「先算一下市场够不够大」的公式，把 M 换算成付费客户数。hatch-counter 可以直接沿用[《定价与商业模式》第 8 章](../pricing-monetization/08-case-hatch-counter.md)的推演假设：每店月付 99 元、每店每月可变成本 15 元、固定成本每月 1500 元，那么净收入每月 2 万元大约需要 256 家付费门店。

**这些金额都是推演用的假设值**，不是 hatch-counter 的真实定价和成本。但即使只是量级，也足够回答一个关键问题：以你每周 10–15 小时，有没有可能在一两年内签下这个量级的客户？如果明显不可能，要么调整定价和客户结构（比如做多店老板），要么接受这个产品在相当长时间里只能是副业。这个问题在阶段 3、4 会反复出现。

## 第 2 周：盘点时间和边界

### 每周真正可用的时间

不要写「每周 15 小时」，要写**具体是哪几个时段**：

```text
# 每周可用时段

周二 20:30–22:30  深度工作（写代码、写文案）
周四 20:30–22:30  深度工作
周六 09:00–13:00  整块：访谈、拜访、渠道实验
周日 20:00–21:00  复盘 + 下周计划
零碎：通勤路上回客户消息、看数据（不计入）

合计约 9 小时整块 + 1 小时复盘
不可用：周一、周三、周五晚上（家庭 / 运动 / 加班缓冲）
```

几条经验：

- **只算整块时间**。半小时以下的碎片只能回消息，做不了需要专注的事
- **给加班留缓冲**。如果公司经常临时加班，每周少算一个时段
- **白天的时段很珍贵**。阶段 1、2 要见门店老板，餐饮老板方便的时间是下午两点到四点半这类非饭点，工作日你多半在上班。周六上午、调休、年假要提前规划给这些事
- **和家人对一遍**。副业占的是家庭时间，提前说清楚哪些时段要用、大概持续多久、什么情况下会停。家人的预期管理在《过渡期收入与个人保障》里有专门一章

### 副业边界核对

> [!WARNING]
> 本节引用的《劳动合同法》第二十三、二十四条按 2025 年前后的现行文本整理，可能已修订，以国家法律法规数据库的现行文本为准；具体合同怎么解释，拿不准时咨询律师。

[《一人公司方法论》第 4 章](../opc-playbook/04-side-to-fulltime.md)「副业期间的边界」讲了框架。阶段 0 要做的是把它落成一次具体的核对，结果写下来：

| 核对项 | 去哪看 | 写下结论 |
|---|---|---|
| 是否禁止兼职、兼职是否需要报备 | 劳动合同、员工手册 | 有 / 无，条款原文 |
| 保密义务覆盖的范围 | 保密协议 | 和副业方向有没有交集 |
| 是否约定了竞业限制、范围和期限 | 劳动合同、竞业协议 | 副业是否在限制范围内 |
| 职务成果的约定 | 劳动合同、知识产权协议 | 有没有「在职期间所有成果归公司」这类宽泛条款 |
| 副业是否和雇主业务有竞争关系 | 自己判断 | 有 / 无 |

竞业限制有法定边界：《劳动合同法》第二十四条规定，竞业限制的人员限于高级管理人员、高级技术人员和其他负有保密义务的人员，解除或终止劳动合同后的竞业限制期限不得超过二年；第二十三条规定约定竞业限制的，用人单位要在竞业限制期限内按月给予经济补偿（条文见 [ecoi.net 收录的《劳动合同法》中文本](https://www.ecoi.net/en/document/270393)）。具体到你的合同怎么解释、是否有效，拿不准时咨询律师，合同条款怎么读见[《合同与法律文书》](../contracts-legal/)。

核对完再做一次「物理隔离」，这是成本最低、收益最高的一步：

- 副业用个人电脑，不在公司电脑上装副业的任何东西，包括 IDE 里登录的个人 GitHub
- 副业代码仓库、云账号、域名、模型 API 账号全部用个人邮箱和个人支付方式
- 公司付费的工具（IDE 授权、AI 编码工具的企业版）不用于副业
- 不在工作时间、工作群里处理副业客户的消息。这一点阶段 2 开始会变难，提前定好规则：客户消息下班后统一回，紧急问题有一个说清楚响应时间的自动回复

## 第 3 周：盘点资产，判断现在处在哪个阶段

### 资产清单

列出你手里已有的、对这个方向有用的东西：

| 类别 | 问自己 |
|---|---|
| 产品 | 已经做到什么程度？能不能给一个陌生人用？ |
| 证据 | 访谈记录、试用记录、付款记录、用户原话，有多少？ |
| 人 | 认识多少个目标用户？认识多少个能介绍目标用户的人？ |
| 行业知识 | 你对这个行业的了解来自亲身经历、二手资料，还是想象？ |
| 渠道 | 有没有已经在用的账号、群、社区身份？ |
| 合规与基础设施 | 域名、备案、服务器、主体，哪些已经办了？ |
| 内容 | 写过的文章、录过的视频、宣传素材 |

### 按证据判断阶段

判断自己在哪个阶段，**只看证据，不看产品完成度**：

| 你手里有的最强证据 | 你在 |
|---|---|
| 只有想法，或者只有产品，没有和目标用户系统聊过 | 阶段 0 末 / 阶段 1 初 |
| 访谈过一批目标用户，问题被确认，但没人付过钱 | 阶段 1 末 / 阶段 2 初 |
| 有几家非熟人客户付了钱 | 阶段 2 |
| 有十家以上付费且多数续费，客户主要来自你本人的人脉 | 阶段 2 末 / 阶段 3 初 |
| 有一个不依赖你本人人脉、能持续带来客户的渠道 | 阶段 3 末 |

产品完成度高、证据少的人，最容易高估自己的阶段。下面用 hatch-counter 做一次完整的盘点。

## hatch-counter 现状盘点

以下根据 hatch-counter 仓库的 README、`docs/` 和提交记录整理，时间截至 2026-11 初。仓库里看得到产品做了什么，看不到线下发生的事（比如和哪些店主聊过），所以「证据」一栏可能低估了实际情况；读者如果就是作者本人，用你知道的线下事实修正这一节。

### 产品与运营能力

- **产品定位**：给一家到几家店的中小餐饮门店用：导入收银报表算销量、拍进货单管库存、记开支算盈亏
- **客户端**：网页端（店主日常用）；安卓移动端（官网可下载的是 0.1.0，代码里的版本更新但还没发）；iOS 走 TestFlight 的流水线还没接
- **服务端与部署**：NestJS + Postgres，一台阿里云 ECS 上 Docker Compose 部署，五个站点（服务端、网页端、管理后台、官网、文档站）都已上线；域名已完成 ICP 备案
- **开户与收费**：只在管理后台开户，分试用（0 元 14 天）、收费开通、内部门店三种；套餐价目改动要复核；客户账单分订单、客户、发票；线下转账、后台确认收款；到期前 7 天、1 天、当天发短信
- **运营后台**：运营分析已有收入、续费率、试用转正率等；识别按次记成本
- **获客素材**：官网一页；一部 30 秒宣传片（竖屏投抖音、视频号，横屏当面演示）；给合作伙伴看的文档站（密码保护）
- **路线图上未做**：在线付款续期、官网「申请试用」、线上告警、备份（目前只有云盘快照）
- **投入强度**：2026-09 初到 11 月初约两个月，一千三百多次提交；其中不少是管理后台各页「二十版」的设计探索

### 证据与渠道

| 方面 | 现状 |
|---|---|
| 访谈记录 | 仓库里没有。规格文档里有对现场的具体描述（站在后厨、冷库门口、手上脏或戴手套），说明作者对场景有了解，但看不出来自几家店 |
| 付费门店 | 仓库里看不到真实付费门店的数量；`mock-data/` 是一家虚构川菜馆的演示数据 |
| 渠道 | 官网写「找客服开户」，开户前那一段在线下；宣传片说明想过短视频渠道；文档站面向合作伙伴，说明想过伙伴渠道。哪个渠道有过实际产出，看不出来 |
| 最近的取舍 | 2026-11 初把管理后台整套客服工单、知识问答、代客办理拿掉了。这是一个好的收敛信号：在没有客户量之前不建客服系统 |

### 结论：产品走在验证前面

把两张表放在一起，结论很清楚：

- **产品能力**已经达到阶段 2 甚至阶段 3 需要的程度：能开户、能收费、能续期、能提醒、能看续费率。很多独立开发者到了几十个客户才补这些
- **证据**停在阶段 0 末到阶段 1 初：看不到系统的访谈记录，看不到付费门店

这不是坏事，它只意味着接下来的工作重心要彻底换一下。按本书的划分，**hatch-counter 现在应该进入阶段 1**，而且可以走一条比从零开始更快的路：带着能用的产品去做验证访谈（第 3 章「带着产品的访谈」）。

同时要警惕两个惯性：

1. **继续打磨产品的惯性**。管理后台每页画二十版、给移动端加功能，这些都是「舒服的工作」。在拿到前十个付费客户之前，产品上只做一类事：**直接挡住某个真实客户试用或付费的问题**
2. **把宣传片和官网当成获客的惯性**。没有验证过「谁会看、看完找谁」之前，素材本身不会带来客户。它们在阶段 2 当面演示时用得上，在阶段 3 渠道实验时用得上，但不是现在的主线

### hatch-counter 进入阶段 1 前的准备清单

- **冻结新功能，路线图上的条目全部移到 `plan/later.md`，标注「等哪个客户信号再做」**
  - 为什么现在做：把时间腾给阶段 1
  - 参考：[《产品思维》第 4 章](../product-thinking/04-mvp-boundary.md)「给推迟的事写上触发条件」
- **准备一家演示店：用 mock 数据生成一家「看得出赚没赚钱」的店，能在手机和笔记本上 5 分钟演示完**
  - 为什么现在做：访谈后半段要用
  - 参考：第 3 章
- **确认官网、登录页上的客服微信能及时响应**
  - 为什么现在做：有人扫码时别让他等两天
  - 参考：—
- **用户协议和隐私政策：确认网页端、移动端、官网都有，且写清收集什么、存在哪**
  - 为什么现在做：一旦有真实门店的数据进来，个人信息和经营数据的义务就开始了
  - 参考：[《国内合规实务》第 6 章](../opc-compliance-cn/06-pipl.md)、《合同与法律文书》
- **识别功能用到视觉模型，确认是否涉及生成式 AI 相关的登记义务**
  - 为什么现在做：收费前要有结论
  - 参考：[《国内合规实务》第 7 章](../opc-compliance-cn/07-generative-ai.md)
- **补每日逻辑备份 + 一次恢复演练**
  - 为什么现在做：真实门店的账丢了，信任就没了
  - 参考：[《一人运维手册》第 2 章](../production-ops/02-backup-dr.md)、[《PostgreSQL 运维》第 2 章](../database-ops/02-backup-restore.md)
- **想清楚第一批钱以什么身份收、怎么给发票**
  - 为什么现在做：阶段 2 第一次收钱前要有答案
  - 参考：[《国内合规实务》第 1 章](../opc-compliance-cn/01-entity-choice.md)、[《财务与税务》第 3 章](../opc-finance/03-invoices.md)

前三项一周内能做完，后四项可以和阶段 1 并行，但要在阶段 2 收第一笔钱之前完成。

## 第 4 周：写下阶段 1 的计划和第一版止损线

阶段 0 的最后一周，把下一阶段的计划写进 `plan/stages.md`：

```text
# 当前阶段：1 问题验证
进入日期：2026-11-24
计划退出：2027-01-19（8 周）
评审日：2027-01-19（写进日历，留半天）

退出条件（全部满足）：
- 访谈至少 8 家目标门店的决策人，其中非熟人不少于 5 家
- 至少 5 家描述了同一类麻烦，且现在正为它花时间或钱
- 至少 3 家同意试用，并对一个具体价格没有否定

止损线（任一成立，进入评审，不自动关停）：
- 到评审日，约到的访谈少于 4 家
- 访谈过的门店里，认为「算不清赚没赚钱」是大问题的不到一半
- 我已经连续 3 周没有推进访谈，且原因不是外部突发事件

整个项目的总止损线（每季度看一次）：
- 2027-05-31 前付费门店少于 5 家
- 累计现金投入超过 ____ 元
```

总止损线的写法见[《一人公司方法论》第 6 章](../opc-playbook/06-when-to-quit.md)。它在阶段 0 写下第一版，每过一个阶段修订一次；修订只能在评审日做，而且要先承认旧标准有没有达到。

## 退出条件、止损线与常见的坑

**退出条件（M0）**：下面四样都写下来了，存在公司仓库里：

1. `plan/numbers.md`：最低可行收入、可动用储蓄、静态跑道
2. 每周可用时段表，家人知道
3. 副业边界核对结果，物理隔离已完成
4. `plan/stages.md`：当前阶段的判断（按证据）、下一阶段的退出条件和止损线

**止损线**：阶段 0 超过 6 周还没完成，通常说明问题不在方法，而在于**每周根本没有可用的时间**。这时不要硬推进，先解决时间问题：和家人重新商量、减少别的投入，或者接受现在不是开始的时候。

**常见的坑**：

| 坑 | 为什么是坑 |
|---|---|
| 先注册公司、买设备、搭一套完美的工具链 | 这些都是阶段 2 以后才需要的；现在做是在用准备工作回避真正的问题 |
| 只算钱不算时间 | 跑道够，每周时间不够，项目一样推不动 |
| 跳过边界核对，觉得「公司不会管」 | 出问题的时候通常是项目做成了的时候，代价最大 |
| 按产品完成度判断阶段 | 会直接跳过验证，去做阶段 3 的渠道 |
| 把止损线写得很模糊，「做不起来就停」 | 模糊的标准等于没有标准，见《一人公司方法论》第 6 章 |

## 本章要点

- 阶段 0 把「大概知道」变成写下来的数字和结论：最低可行收入、时间、边界、资产、当前阶段
- 最低可行收入用真实账单算，把单位现在承担的部分列出来；再换算成需要的付费客户数，判断量级是否现实
- 时间写成具体时段，只算整块时间；见门店老板要用白天，提前规划周末和假期
- 对照劳动合同和员工手册做一次边界核对；竞业限制期限法定不超过二年，需按月补偿；副业的设备和账号与公司彻底分开
- 判断阶段只看证据，不看产品完成度
- hatch-counter 的产品能力已到阶段 2–3，证据停在阶段 0 末到 1 初；接下来冻结新功能，带着产品进入阶段 1
- 阶段 0 的结尾写下阶段 1 的退出条件、止损线和项目的总止损线

# 把需求写下来

一个人做产品，很容易觉得「需求都在我脑子里，不用写」。但脑子里的需求是模糊的、会变的、只有你自己能读的。这一章讲为什么一个人也要写需求文档，以及两种最有用的文档怎么写：一页需求和页面规格。素材主要来自 hatch-counter 的 `docs/策划/` 目录，那是一套真实在用的需求与页面规格。

相对 ROADMAP 原大纲，这一章是新增的。原因很简单：有了编码 agent 之后，「把需求写清楚」直接决定了 agent 写出来的东西对不对，值得单独讲。

## 一个人为什么也要写

写下来不是为了走流程，而是因为至少有三个读者需要它：

| 读者 | 他需要什么 | 不写的后果 |
|---|---|---|
| 未来的你 | 三个月后回来改这个功能时，知道当初为什么这么定 | 改掉了一个「看起来多余」、其实踩过坑的设计 |
| 编码 agent | 明确的目标、边界和验收标准 | 它会按自己的理解补全空白，常常补错 |
| 测试的人（往往也是你） | 每种情况下屏幕上应该是什么 | 只测了正常路径，空态、出错、没权限都没测 |

第二个读者是这几年新增的，也是最重要的。你写给 agent 的需求越清楚，它返工越少。而且一份写在仓库里的规格，agent 每次都能读到，不用你每次在对话里重新解释。

写的过程本身也有价值：很多问题在写的时候才会暴露出来。「这里没有数据时显示什么？」「这个按钮谁能点？」写不下去的地方，就是还没想清楚的地方。

## 一页需求

对一个新功能，在动手之前写一页需求就够了。不需要几十页的需求说明书，一页能写清楚的，说明你已经想清楚了；一页写不完的，说明范围太大，该拆了。下面以路线图上的「工资单导出」为题写一份示意，列和人数都是虚构的：

```markdown
# 工资单导出给会计

## 问题
月底结完工资，店主要把明细交给代账会计。现在只能在工资页截图，
会计拿到后还要手敲一遍，容易错。近一个月有 3 位店主提到（见需求池）。

## 怎么算解决了
店主在工资页点一下，拿到一个会计能直接打开、直接用来算账的文件。

## 方案
在工资页加「导出 Excel」，导出当前所选月份、所有已确认员工的明细。
列：姓名、岗位、出勤天数、基本工资、加班、扣款、实发。

## 不做
- 不做会计专用账号或只读权限（另一个方案，先看导出够不够用）
- 不导出未确认的月份（数还会变）
- 不做 PDF

## 未决问题
- 会计常用的列顺序是什么？找一位店主要一份会计现在用的表

## 验收
- 选一个已确认的月份，导出的文件用 Excel 和 WPS 都能打开，金额和页面一致
- 未确认的月份，导出按钮灰着，悬停说明原因
- 没有工资页权限的人看不到按钮
```

几个要点：

- **问题放在最前面**，并且引用来源（需求池、访谈）。这是第 3 章的问题陈述
- **「不做」一定要写**。它是第 4 章「非目标」在功能级别的版本
- **「未决问题」诚实列出来**。写不出答案的地方，比假装写出答案好
- **验收用能照着点一遍就判对错的句子**

## 页面规格

一页需求回答「做什么、为什么」；页面规格回答「做成什么样」：用户在这一页看见什么、能点什么、点了会怎样、每种情况下屏幕上是什么。

hatch-counter 的 `docs/参考/策划页写法.md` 规定了每一页规格的结构，按这个顺序往下写，用不上的节整节不写：

| 节 | 写什么 |
|---|---|
| 回答什么 | 一两句：用户打开这一页是想知道什么、办什么事；谁看得见 |
| 从哪进 | 导航位置、地址、别的页上哪几处会跳过来 |
| 摆什么 | 从上往下：页头、工具条、主体、底部；每块写清数据从哪来、空的时候是什么 |
| 能做什么 | 每个动作一条：按钮上的字、谁能点、点了会怎样、要不要确认、成了是什么样、撤不撤得回 |
| 各种状态 | 一张表：状态、什么时候出现、屏幕上是什么 |
| 文案 | 这一页固定要出现的字：页头说明、空态、确认框、提示 |
| 接口 | 读哪几条、写哪几条，一句说明各管什么 |
| 验收 | 一条一句、能照着点一遍就判对错的清单 |

这个结构值得借鉴的地方有几个。

### 「回答什么」放在第一节

每一页规格的第一句，不是「这一页有哪些组件」，而是「用户打开这一页想知道什么」。hatch-counter 移动端总纲的页面清单里，每一页都有一列「回答什么」：

| 页 | 回答什么 |
|---|---|
| 门店概览 | 今天卖了多少、比上周同一天怎样、这个月累计、该补几样料、还欠多少钱 |
| 营业明细 | 这段时间营收多少、比前一段怎样、哪个时段、哪些菜 |
| 库存管理 | 要进货什么、每样还有多少够撑几天、进出流水 |

一页回答不了一句话的问题，往往就是这一页塞了太多东西。总纲里有一条原则「一屏回答一个问题」，理由是：网页端的大表不往手机上搬，搬了谁也看不完。

### 状态表

大多数页面规格只写了「有数据、一切正常」时的样子。而实际上用户经常看到的是其他状态。一张状态表能把它们逼出来：

| 状态 | 什么时候出现 | 屏幕上是什么 |
|---|---|---|
| 加载中 | 第一次进入，还没取到数 | 骨架屏，不显示「0」 |
| 空 | 一条记录都没有 | 一句说明 + 引导去做第一件事 |
| 筛完没有 | 有数据，但当前筛选条件下没有 | 「这几天没有」+ 清除筛选，和「空」区分开 |
| 读不到 | 网络或服务端出错 | 已有旧数据就照摆、顶上提示；没有才整块说「没取到」+ 再试一次 |
| 没权限 | 当前用户没有这一页的权限 | 页面不出现在导航里；硬闯进来时说清找谁开 |
| 只读 | 有看的权限，没有改的权限 | 写的入口灰着，说明找谁放开 |

注意「空」和「筛完没有」要分开：前者要引导用户开始用，后者要让用户知道是筛选条件的问题。「读不到」那一行也有讲究：hatch-counter 的原则是「取不到不清屏」，已经有数据时，这次没取到不应该把屏幕清空。

一个页面特有的状态，也要写进去。比如「拍单补仓」的规格里，识别那一步有「认着」「没认出来」两个状态，校对那一步还有「像是录过了」「合计对不上」「还有几处要你定」几种情况，每种都写了屏幕上出现什么字、按钮是什么状态。

### 文案写进规格

按钮上的字、空态的说明、确认框里的那句话，都应该写进规格，而不是留给写代码时临时想。原因是：**文案就是交互的一部分**。

比较两种确认框：

```text
确定要删除吗？
[取消] [确定]
```

```text
不录这一张了？
拍的这张和你定的、改的都不留，回头要录得重拍。
[接着校对] [不录了，这张不要了]
```

第二种来自 hatch-counter 的拍单补仓规格。它说清了后果，按钮上的字说清了点了会怎样。网页端总纲里有一条原则：按钮写清点了会怎样（「确认补仓」「记下这笔」，不写「确定」）。这类细节，不写在规格里，写代码时一定会被「确定 / 取消」糊过去。

文案怎么写得好，《文案与内容》会专门讲；这里只要记住：**文案在规格阶段就定下来**。

### 验收清单

规格的最后一节是验收清单，每一条都是一个可以照着做、能判断对错的动作。下面几条是照拍单补仓规格里的描述整理的示意：

```markdown
## 验收

- 一张单子认出 15 行、有 2 处名字对不上：头上写「2 处要你定」，主按钮灰着写「还有 2 处要定」
- 定完 2 处：头上变成「都定好了」，主按钮变成「录进库存 · 14 样 · ¥612」
- 断网时点录入：顶上提示没录进去，拍的、改的都还在；恢复网络再点，只录一张
- 校对时点返回：从底下问「不录这一张了？」，选「不录了」后照片删掉
- 没有库存「改」权限的人：顶上一句说明，能拍的都灰着
```

这份清单有三个用途：你自己写完代码后照着点一遍；交给 agent 时作为验收标准；以后改动这一页时作为回归测试的依据。很多条目还可以直接变成自动化测试用例。

## 规格和「为什么」分开放

规格写的是「现在要的样子」。但很多设计背后有一段来历：为什么这么定、踩过什么坑、考虑过哪些别的方案。这些信息很重要，但如果都塞进规格，规格会变得又长又难读。

hatch-counter 的做法是分两处：

| 目录 | 写什么 | 读者 |
|---|---|---|
| `docs/策划/` | 看得见的：每一页摆什么、能做什么、各种状态 | 写界面的人、画稿的人、测的人 |
| `docs/现行/` | 算法、口径、为什么这么定、踩过的坑 | 改逻辑的人、将来的自己 |

两边对不上时，以策划为准，再去改代码。规格里需要引用某个算法时，链到现行页，而不是抄一份。

一句话能说完的理由，直接挂在那条规矩后面，比如「看数的页不改数。看的地方能改，人在翻数的时候会误碰」。说来话长的，放到另一处。

hatch-shelf 用的是另一种形式：设计文档最后一节是一张「决策记录」表，三列：决策、结论、理由：

| 决策 | 结论 | 理由 |
|---|---|---|
| 渲染方式 | WebView 而非 RN 原生 Markdown 组件 | 原生组件对代码高亮、公式、Mermaid、宽表格的支持弱 |
| 数据源 | 文件即真相，SQLite 只做索引 | 索引可重建；以后加任何同步通道，阅读器都不用改 |

一个人做产品时，这张表特别有用：几个月后你想推翻某个决定时，先看看当初的理由还成不成立。

## 交给 agent

写好的规格放在仓库里，就成了 agent 的输入。几个让它发挥作用的做法：

- **在 `CLAUDE.md` 里指明规格在哪**。hatch-counter 的 `CLAUDE.md` 写着：新功能的需求和页面规格写进 `docs/策划/<端>/`，跟现行对不上时以策划为准
- **一次只交一页**。「照 `docs/策划/移动端/拍单补仓.md` 实现校对那一步」比「实现拍单补仓」好得多
- **先让它读、再让它提问**：

```text
读 docs/策划/网页端/工资结算.md 和它链到的现行页。
先不要写代码。列出：
1. 规格里没写清楚、你需要我决定的地方
2. 规格和现有代码对不上的地方
3. 你打算改哪些文件
等我回复后再动手。完成后按「验收」一节逐条自查并报告结果。
```

- **让 agent 帮你补规格**，而不只是读规格：「这一页的状态表还缺哪些状态？」它在列举边缘情况上往往比人细致
- **改完代码，同步改规格**。规格和代码脱节以后，就不再是任何人的真相了

## 写到什么程度

不是每个改动都需要完整的页面规格。一个大致的标准：

| 改动 | 写什么 |
|---|---|
| 修一个文案、调一个颜色 | 不用写，提交信息里说清楚 |
| 小功能，一个按钮、一个字段 | 需求池里那一条补上「怎么算解决了」和验收 |
| 新功能，涉及一两个页面 | 一页需求 |
| 新页面、新流程、涉及钱和数据 | 一页需求 + 页面规格 |
| 改变产品方向或架构 | 写进设计文档和决策记录 |

## 本章要点

- 写需求是为了未来的自己、编码 agent 和测试；写不下去的地方就是没想清楚的地方
- 新功能先写一页需求：问题、怎么算解决了、方案、不做、未决问题、验收
- 页面规格按固定结构写：回答什么、从哪进、摆什么、能做什么、各种状态、文案、接口、验收
- 「回答什么」放第一节；一页回答不了一句话的问题，就是塞多了
- 状态表把加载、空、筛完没有、读不到、没权限、只读逼出来
- 文案在规格阶段定下来；按钮写清点了会怎样，确认框说清后果
- 规格写看得见的样子，「为什么」放在现行文档或决策记录里
- 规格放仓库、在 `CLAUDE.md` 指明位置，一次交给 agent 一页，让它先提问再动手

# 测试数据与 fixture

写测试最费事的部分往往不是断言，而是准备数据：一条「店员没权限时看到正确提示」的测试，需要一家店、一个店主、一个店员、一组权限设置，可能还需要几条开支记录。数据准备写得随意，测试就会变得又长又脆，几十条测试各自复制一份建店代码，改一个必填字段要改几十处。这一章讲测试数据的几种来源、怎么组织它们，以及一类特别有价值的数据：一套手工核对过每个数字的样例账。

「fixture」这个词有两层意思：一是测试用的固定数据（一个样例文件、一组种子数据），二是测试框架里「为测试准备好、用完自动清理的东西」（Vitest 的 `test.extend`、Playwright 的夹具）。这两层这一章都会讲。

## 测试数据的五种来源

| 来源 | 例子 | 适合 |
|---|---|---|
| 字面量 | 测试里直接写的对象、字符串 | 单元测试，数据量小 |
| 当场生成 | 测试里用代码拼出一个压缩包 | 二进制或结构化输入 |
| 工厂函数 | `seedStore(db, "街角面馆")` | 集成测试和端到端测试的前置数据 |
| 样例数据集 | 一家虚构门店四个月的完整账目 | 跨模块的计算口径、演示 |
| 录制的真实样本 | 第三方 API 的真实响应、旧客户端的真实请求 | 契约和兼容性 |

还有一种常被忽略的来源：**真实内容本身**。hatch-shelf 的 `books/` 目录下放着全部书稿，`pnpm shelf-pack check books/` 用 `@shelf/spec` 里的同一套规则把每一本都校验一遍：唯一 H1、代码块标了语言、链接指向存在的章节和小节。这相当于一个用全部真实数据跑的测试，规则有误判时，第一时间在真实内容上暴露出来。

## 字面量和当场生成：让数据和断言放在一起

单元测试里，数据最好就写在测试里，读测试的人不用跳到别的文件就知道输入是什么。

hatch-shelf 的导入测试需要压缩包作为输入。它没有在仓库里放一堆 `.zip` 文件，而是用 `fflate` 当场拼：

```typescript
const yaml = "id: demo\ntitle: 示例\nchapters: [01-a.md, 02-b.md]\n";
const zip = (files: Record<string, string | Uint8Array>) =>
  zipSync(Object.fromEntries(Object.entries(files).map(([k, v]) => [k, typeof v === "string" ? strToU8(v) : v])));

it("strips a single wrapping directory and macOS junk", () => {
  const r = prepareImport({
    kind: "zip",
    fileName: "demo.zip",
    bytes: zip({
      "demo/book.yaml": yaml,
      "demo/01-a.md": "# A",
      "demo/02-b.md": "# B",
      "__MACOSX/demo/._01-a.md": "x",
      "demo/.DS_Store": "x",
    }),
  });
  expect(r.ok && r.files.map((f) => f.path).sort()).toEqual(["01-a.md", "02-b.md", "book.yaml"]);
});
```

压缩包里有什么一目了然：一层包裹目录、两个 macOS 自动生成的垃圾文件。如果这是仓库里的一个二进制文件 `fixtures/wrapped-with-junk.zip`，读者得解压才知道它测的是什么，而且没人会注意到某天它被替换成了内容不同的另一个文件。

**什么时候该把样本存成文件**：样本是从外部来的、你无法用代码准确复现的时候。比如供货商导出的 Excel 送货单，它的列名、合并单元格、日期格式是对方系统决定的，用代码拼出来的「仿制品」恰恰会漏掉那些让解析出错的怪异之处。这类文件存进仓库，文件名写清来源和特点。

## 工厂函数：只写这条测试关心的字段

集成测试和端到端测试需要一组合法的前置数据。工厂函数的设计原则是：**给每个字段合理的默认值，测试只覆盖它关心的那几个**。

```typescript
let seq = 0;
const next = () => ++seq;

export function expenseInput(overrides: Partial<ExpenseInput> = {}): ExpenseInput {
  const n = next();
  return {
    expenseDate: "2026-10-16",
    periodFrom: "2026-10-16",
    periodTo: "2026-10-16",
    amountCents: 8500,
    title: `开支 ${n}`,
    categoryId: "",
    ...overrides,
  };
}
```

```typescript
it("跨月的开支按天摊到两个月", async () => {
  const body = expenseInput({ periodFrom: "2026-10-20", periodTo: "2026-11-09", amountCents: 21_000, categoryId });
  // ……
});
```

读这条测试，能看出它关心的是摊销区间和金额，其余字段无关紧要。如果把整个对象都展开写出来，关键的两个字段就淹没在十个无关字段里了。

几个细节：

- **用序号保证唯一**：标题、手机号这类有唯一约束或者需要区分的字段，用递增序号生成，不要用随机数。hatch-counter 的幂等测试里，手机号从 `13760000000` 开始逐条加一，出问题时能从手机号推出是第几个租户
- **默认值要合法，而且要「无聊」**：默认的金额、日期不要落在任何边界上，否则一条本来不关心边界的测试会意外地测到边界
- **工厂只造数据，不藏断言**：工厂里出现 `expect`，说明它在偷偷测别的东西

### 种子函数要写清「捷径」

工厂函数写数据库时，经常绕过正常的业务流程。hatch-counter 的 `seedStore` 直接往表里插账号、门店和成员关系，跳过了管理后台的开户流程。它的注释写清了这一点：

```typescript
/**
 * 造一个「账号 + 门店」，返回 id。多租户的测试至少要两家店才说明问题。
 *
 * 这是绕过管理后台的捷径：正经开户走 `POST /v1/admin/stores`，那条路在
 * `admin.e2e.test.ts` 里专门验。别的测试只是需要一家能用的店，不该每个都先登一次后台。
 * 带上 `phone` 就顺手把登录凭证也建了——客户端现在是邀请制，没有凭证根本登不进来。
 */
export async function seedStore(owner: postgres.Sql, name: string, opts: SeedStoreOpts = {}) {
  // ……
}
```

这段注释回答了三个问题：为什么可以走捷径（正规路径在别处验过了）、捷径省了什么（每条测试先登一次后台）、有什么坑（不带手机号就没有登录凭证）。走捷径的种子函数，最大的风险是**和真实流程造出的数据不一样**：正规开户会顺手建一些默认分类，捷径没有，于是某条测试在捷径数据上是绿的，真实用户却会遇到问题。注释写清楚，至少让人知道该去哪里对照。

## 测试框架里的 fixture

> [!WARNING]
> Vitest 的 `test.extend` 后来陆续加入了 `auto`、`scope: "file"` / `"worker"` 等选项；这些选项的可用性和语法以 Vitest 官方文档 Test Context 一节为准。

Vitest 的 `test.extend` 把「准备数据」和「清理」打包成一个可以按需注入的东西：

```typescript
import { test as base } from "vitest";
import { openTestDb, resetDb, seedStore, type TestDb } from "./helpers/db";

type Fixtures = {
  db: TestDb;
  store: { storeId: string; accountId: string };
};

export const test = base.extend<Fixtures>({
  db: async ({}, use) => {
    const db = await openTestDb();
    await resetDb(db.owner);
    await use(db);
    await db.close();
  },
  store: async ({ db }, use) => {
    await use(await seedStore(db.owner, "街角面馆", { phone: "13600000001" }));
  },
});
```

```typescript
test("新开的店没有任何开支", async ({ db, store }) => {
  // db 和 store 已经准备好
});

test("只用到数据库的测试不会建店", async ({ db }) => {
  // 没有声明 store，store 的准备代码不会执行
});
```

比起 `beforeEach`，fixture 有三个好处：**按需**（测试不声明就不准备）、**可组合**（`store` 依赖 `db`，框架负责顺序）、**清理和准备写在一起**（`use` 之后的代码就是清理）。

## 让数据可复现

> [!WARNING]
> `@faker-js/faker` 的 API（`faker.seed`、各模块的方法名、中文 locale 的导入路径）在大版本之间变化较大，以官方文档为准。

测试数据里任何随机的东西，都会让失败变得无法复现。三个来源要管住：

| 来源 | 问题 | 做法 |
|---|---|---|
| 时间 | 「今天」每天不同，月末、跨年时测试突然红 | 时间作为参数传入（见[第 2 章](02-unit-vitest.md)），或用固定的假时钟 |
| 随机数 | 失败的那组数据再也找不回来 | 不用随机数造数据；非用不可就固定种子，并在失败信息里打印种子 |
| 自增 id 和顺序 | 断言了 `id === 1`，换个执行顺序就错 | `restart identity` 重置序列；更好的做法是不断言具体 id |

用 faker 这类库生成「看起来真实」的数据时，记得固定种子：

```typescript
import { fakerZH_CN as faker } from "@faker-js/faker";

faker.seed(20261104);
const name = faker.person.fullName();
```

即便如此，随机生成的数据对测试的帮助有限：它看起来真实，但不会刻意落在边界上。边界值还是要手写。

有一类时间问题需要特别注意：**依赖「今天」的种子数据**。hatch-counter 的演示账（给应用商店审核员看的那一家店）按「今天往前推若干天」生成。它有一条专门的测试，起因是一个只在特定日期才会出现的问题：种子写的周期开支规则如果比它实际写入的第一期还早，客户端第一次打开开支页时会把「缺失」的几期自动补出来，审核员就会看到一年前没付的房租和社保，看上去像系统坏了。测试把生成的起点刻意放在两个月前的 10 号，让 5 号、8 号和 15 号记账的规则分别落在起点前后，两种情况都覆盖到。

## 样例数据集：一家手工核对过的店

hatch-counter 仓库里有一个 `mock-data/` 目录，它是一家虚构的川菜馆「蓉香小馆」从开店建档到营业四个月的全部原始资料：手写的进货单照片、Excel 送货单、美团收银的品项销售明细、水电燃气账单、考勤和工资，最后还有一张盘点表。

配套的操作手册按顺序引导你把这些资料一个月一个月录进系统，每一步后面有一个「做对了应该看到什么」的标记，手册开头写着：这些数不是估的，已经按完整流程逐一核对过。

这套数据还**故意埋了很多事**：七夕、中秋、国庆的销量波动，八月上新菜，猪肉涨价、九月回锅肉跟着涨价，员工入职离职、旷工，停电歇业一天，一份配方写偏了。手册附录里有完整清单，并提示「做的时候先别看」，看系统的经营分析能不能自己把这些点出来。

这样一套数据的价值是多方面的：

- **它是计算口径的对照值**。毛利、成本、库存、工资都有手工算出的正确答案，任何一处口径改动，对照值对不上就说明有问题
- **它覆盖了真实的混乱**。四家供货商四种单子格式，月结和现结，周期不同的结算日。这些是用工厂函数拼不出来的
- **它是验收测试**。新功能做完，按手册走一遍，比任何单元测试都更接近店主的真实使用
- **它是演示和文档**。新来的人（或者编码 agent）按手册走一遍，就理解了整个产品

它的代价是制作成本很高，而且口径一改就要重新核对。所以它不适合当日常的自动化测试数据，而是作为一个**基准**：服务端分析模块的测试里，核心场景的断言是钉死的对照值。hatch-counter 的开发文档里有一条明确的规矩：分析测试的断言是钉死的对照值，不要为了让测试通过顺手改；口径改了测试会红，那是它在工作，口径确实要改就连测试一起改。

> [!IMPORTANT]
> 钉死的对照值最怕被「顺手更新」。不管是人还是编码 agent，看到断言失败就把期望值改成实际值，测试立刻失去意义。把这条规矩写进项目的说明文件（`CLAUDE.md` 或开发文档），并在测试文件开头用注释重复一遍。

## 录制的真实样本

[第 3 章](03-test-doubles.md)和[第 5 章](05-api-contract.md)都提到过：第三方 API 的响应、旧客户端的请求，要用真实的样本，而不是照着文档手写。

保存样本时有几条规矩：

- **去掉敏感信息**：令牌、手机号、身份证号、真实的店名和金额。替换成明显是假的值（`13600000001`、`测试店`），而不是删掉字段，删字段会改变数据的结构
- **记录来源**：样本文件旁边放一行说明，写明从哪里、在哪天、用哪个版本录的。半年后对方改了接口，你需要知道手里的样本有多旧
- **原样保存**：不要「整理」样本，比如格式化 JSON、补上缺失的字段。真实响应里的怪异之处，正是测试需要覆盖的东西

> [!CAUTION]
> 永远不要把生产数据库的数据直接拷贝出来当测试数据。哪怕仓库是私有的，测试数据也会出现在 CI 日志、错误截图、编码 agent 的上下文里。需要真实规模的数据时，用脱敏脚本处理后再用，或者像蓉香小馆那样完全虚构。

## 数据准备的坏味道

| 坏味道 | 表现 | 改法 |
|---|---|---|
| 神秘访客 | 测试依赖某个共享 fixture 里的数据，但测试本身看不出来 | 测试需要的关键数据在测试里显式创建 |
| 万能 fixture | 一个 `setupEverything()` 建了所有测试可能需要的数据 | 拆成小工厂，按需组合 |
| 复制粘贴的准备段 | 几十条测试开头都是同样的十行 | 提取成工厂或 fixture |
| 准备段比断言长十倍 | 为了测一件小事构造了整个世界 | 被测单元太大，或者应该在更低的层测 |
| 共享可变 fixture | 前一条测试修改了数据，后一条测试的结果取决于执行顺序 | 每条测试自己的数据；或每条测试一个新租户 |

「神秘访客」最隐蔽。比如一条测试断言「列表里有 3 条记录」，而这 3 条来自一个全局种子文件。某天有人往种子文件里加了一条，这条测试红了，修的人完全不知道它和种子文件有关。

## 本章要点

- 测试数据有五种来源：字面量、当场生成、工厂函数、样例数据集、录制的真实样本；真实内容本身也能当测试数据
- 单元测试的数据写在测试里；只有外部来的、无法用代码复现的样本才存成文件
- 工厂函数给合法而「无聊」的默认值，测试只覆盖关心的字段；唯一字段用序号不用随机数
- 走捷径的种子函数要写清楚绕过了什么、正规路径在哪里验
- Vitest 的 `test.extend` 让数据按需准备、自动清理、可以组合
- 管住时间、随机数和自增 id；依赖「今天」的种子数据要专门测
- 一套手工核对过的样例数据集是口径的基准；钉死的对照值不能顺手更新
- 录制的样本要脱敏、记录来源、原样保存；不要拷贝生产数据
